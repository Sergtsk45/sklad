# Supply cycle actions context

**Ключевые слова**: снабжение, закупка, требование, приход, O001, O002, ОбМ, object.request, purchase.order, stock.picking, УТ-1132

## Роли

- Прораб: создает `object.request`, указывает объект/проект, срок и строки потребности.
- Снабженец: разбирает OR, выбирает "с базы" или "закупка", готовит PO/internal picking, завершает Confirm/Validate в UI.
- Кладовщик или прораб объекта: принимает факт и сверяет метраж.
- AI: ищет товары, остатки, склады и готовит только черновики OR/PO/picking после UI-подтверждения.
- Бухгалтерия: счет, оплата, НДС и банк ведутся в 1С, не в Odoo.

## Склады объектов и picking type

Production-объектные склады имеют коды `O001` и `O002` и связаны с `object.request.project`. Для PO нужен `stock.warehouse.in_type_id` выбранного склада (любой склад: `O002`, `Ос.ск`, «Основной склад» и т.д.). Для внутреннего перемещения на объект нужен `stock.warehouse.int_type_id`, назначение — `stock.warehouse.lot_stock_id` объектного склада.
Tool `find_warehouse` принимает `query`: код (`O002`, `O001`, `Ос.ск`) или часть названия/адреса (`Хмельницкого`, `Ломоносова`, `Основной склад`). Legacy aliases временно поддерживаются: `ОбМ-2` → `O001`, `ОбМ-4` → `O002`; `search_stock_quants.warehouse_codes` нормализует эти aliases так же.

| Объект | Код склада | PO incoming picking type | Internal picking type |
|---|---|---|---|
| Ломоносова 164 | O001 | `O001: Поступления` (`in_type_id`) | `O001: Внутренние переводы` (`int_type_id`) |
| Б. Хмельницкого, 112 | O002 | `O002: Поступления` (`in_type_id`) | `O002: Внутренние переводы` (`int_type_id`) |

Если потребность относится к объекту, но приёмка на центральный склад — после PO может понадобиться internal picking на объект `O001` или `O002`.

## Количество труб

До закрытия TD-002 AI только подсказывает пересчет, но записывает в строки уже согласованные метры:

- штуки хлыстов: `шт * длина_хлыста`;
- килограммы: `кг / кг_на_метр`;
- тонны: `т * 1000 / кг_на_метр`.

Пример УТ-1132: 1.5*12 + 15*12 + 13*6 + 51*6 + 30*6 + 56*6 = 1098 м.

## Denylist процесса

AI не вызывает `button_confirm`, `button_validate`, `action_done`, `action_post` из свободных LLM tools; не пишет `state` напрямую; не использует `stock.quant.write/create/unlink` и inventory adjustment; не создает платежи (`account.payment`); не работает с `res.users`, `res.groups`, `ir.model.*`, `ir.ui.*`; не удаляет проведенные документы.

Исключение: детерминированный `InvoiceWorkflow` после кнопки **«Выполнить»** может вызвать `button_confirm`, `button_validate` и создать **черновик** vendor bill (`account.move`), если пользователь ответил «Да» на «Привязать счёт?». `action_post` и оплаты не вызываются.

Остатки появляются только после штатного Validate в UI или после закрытия TD-003. Прямой перевод picking в `done` через API дает документ без quants.

## Правильный план PO

Для запроса "создай PO по счету УТ-1132 на O002" или legacy "создай PO по счету УТ-1132 на ОбМ-4":

1. Найти OR и объект: `origin = OR/...`.
2. Найти склад `O002` через `find_warehouse` (legacy `ОбМ-4` тоже должен резолвиться в `O002`), взять `in_type_id`.
3. Найти поставщика по ИНН/имени, проверить `supplier_rank > 0`.
4. Найти товары, проверить `is_storable = true`.
5. Показать план и дождаться кнопки подтверждения.
6. Создать `purchase.order` в `draft`: `partner_id`, `picking_type_id = O002.in_type_id`, `origin`, `partner_ref = УТ-1132`.
7. Добавить строки в метрах; для труб с UoM не метр - вернуть предупреждение.
8. Записать note в chatter: создано AI-ассистентом, пользователь, источник и краткая сводка.
