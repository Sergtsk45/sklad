# Odoo: каталог товаров (карточки и алиасы)

Переносимый workflow для складского агента. Работает в любом проекте с Odoo
Inventory/Purchase и MCP. **Не хардкодь** URL базы, id категорий, id UoM,
имя MCP-сервера — ищи по имени в текущей базе.

Примеры имён — [naming-examples.md](naming-examples.md).  
Примеры RPC — [examples.md](examples.md).  
Локальные id категорий проекта — правило/скилл в репозитории (если есть).

## Главные правила

- Меняй данные **только** по явной команде: «создай», «добавь», «нормализуй»,
  «повесь vendor», «сливай». Вопрос «можешь ли / есть ли?» — сверка и план,
  без create/write.
- Модель: **один типоразмер = одна карточка**, много поставщиков через
  `product.supplierinfo`.
- В `product.template.name` — **без бренда и поставщика**. Бренд, торговое
  имя, артикул, цена — в алиасе поставщика.
- Материалы (`type=consu`): **`is_storable=true`**. Услуги (`type=service`):
  без складского учёта.
- Не удаляй (`unlink`) карточки с движениями — только `active=false`.
- Имя MCP-сервера разное: найди сервер Odoo через каталог MCP.

## Термины

| Термин | Модель / поле | Смысл |
|--------|---------------|--------|
| Карточка | `product.template` | Нормализованный товар для остатка и выдачи |
| Алиас / vendor | `product.supplierinfo` | Артикул, торговое имя, цена у поставщика |
| Типоразмер | — | Ду/DN, PN/Ру, толщина, материал, IP, цвет (если важен), длина |

## Чеклист (счёт → каталог)

```
- [ ] Явная команда на запись (если нужна запись)
- [ ] Поставщик найден / создан (отдельный скилл контрагента)
- [ ] Каждая строка: поиск по коду → типоразмеру → имени
- [ ] Вердикт: есть / частично / нет
- [ ] План имён и категорий (если «только проверь» — стоп здесь)
- [ ] Create/update карточек + supplierinfo
- [ ] name на lang каталога (часто ru_RU) + en_US
- [ ] Chatter: номер счёта / причина
- [ ] Отчёт пользователю
```

## Шаг 1 — Сверка позиции с базой

Для каждой строки счёта ищи в порядке:

1. **Артикул** в `product.supplierinfo.product_code` (и при необходимости
   `default_code` на шаблоне).
2. **Типоразмер** в `name` (Ду, PN, мм, IP, цвет, длина) — `ilike` по ключам,
   `context.lang` = язык UI каталога, `active_test=false` при поиске дублей.
3. **Близкие по смыслу** карточки (тот же тип, другой PN/IP/толщина) —
   помечай «частично», не считай точным совпадением.

### Вердикт

| Статус | Действие при команде «создай» |
|--------|-------------------------------|
| **есть** | Не создавать; обновить/добавить алиас этого поставщика |
| **частично** | Не создавать дубль; уточнить или повесить vendor на мастер |
| **нет** | Создать нормализованную карточку + алиас |

Частичное ≠ точное: PN10≠PN16, IP54≠IP66, 0,75≠1,5, 20×20≠25×25,
манжета ≠ переход в сборе.

## Шаг 2 — Нормализованное имя

Формат: **тип + ключевые размеры + материал/исполнение** (кратко).

- Марка/класс товара (ОК 46.00, E-46 Premium, ЩМП IP66) — **в имени**, если
  это типоразмер, а не бренд.
- Бренд (FERAT, Альфа Глобал, TDM, CHINT) — **только в** `product_name`.
- Упаковка «15 шт в коробке» — в `product_name`, не в `name`.

См. таблицу плохо/хорошо в [naming-examples.md](naming-examples.md).

### Язык `name` (translate=True)

В Odoo 16+ `name` часто JSONB. UI на `ru_RU` ищет русский перевод.

1. create/write `name` с `context={"lang": "<язык каталога>"}` (часто `ru_RU`).
2. Сразу синхронизируй тот же текст на `en_US` (и другие используемые lang).
3. Если MCP `update_record` **не умеет** передать `lang` — используй XML-RPC /
   shell с context, не оставляй имя только в source/en_US.
4. После переименования проверь поиск в UI на языке каталога.

## Шаг 3 — Создать карточку (если нет)

Резолви id по имени в текущей базе:

- категория: `product.category` (`complete_name` / `name`);
- UoM: `uom.uom` (`шт.`, `метр`, `кг`, …).

```text
create_record(
  model="product.template",
  values={
    "name": "<нормализованное имя>",
    "categ_id": <id категории>,
    "uom_id": <id ед.изм.>,
    "type": "consu",              # или "service" для услуг
    "is_storable": true,          # false для service
    "purchase_ok": true,
    "sale_ok": false,
    "standard_price": <цена>,
    "list_price": <цена>
  }
)
```

`default_code` на шаблоне — только если это **внутренний** код; артикул
поставщика лучше в `product.supplierinfo.product_code`.

### Выбор UoM

| Как продают / учитывают | UoM |
|-------------------------|-----|
| Штуки, хлысты фиксированной длины (L6 м) | шт. |
| Погонные метры без фиксации длины | метр |
| Цена в счёте за кг (лист, электроды) | кг |
| Услуга (резка, доставка) | шт. или усл., `type=service` |

Если цена в счёте за кг, а карточка в шт. — в алиасе пиши цену **в UoM
карточки** (пересчитай из суммы/количества) и в `product_name` оставь
формулировку счёта.

## Шаг 4 — Алиас поставщика (`product.supplierinfo`)

На **существующей** или только что созданной карточке:

```text
create_record / update_record(
  model="product.supplierinfo",
  values={
    "product_tmpl_id": <id шаблона>,
    "partner_id": <id поставщика>,
    "product_code": "<артикул со счёта или false>",
    "product_name": "<торговое имя со счёта>",
    "price": <цена в UoM карточки>,
    "min_qty": 1.0
  }
)
```

Правила:

- Ищи строку того же `partner_id` + того же `product_code`; есть → **update**,
  нет → **create**.
- Не затирай алиасы **других** поставщиков.
- Несколько брендов на одном типоразмере = несколько строк одного или разных
  `partner_id`.
- Дубли пустых строк того же partner (без кода) после появления строки с кодом
  — удали пустые, оставь каноническую.

## Шаг 5 — Chatter

На карточке зафиксируй источник:

```text
post_message / message_post:
  «<№ счёта> <поставщик> <дата>: <артикул>, цена … . <уточнение>.»
```

## Слияние дублей

Только по явной команде «сливай».

1. Выбери **мастер** (история PO, остаток, более полное нормализованное имя).
2. Перенеси все `product.supplierinfo` на мастер.
3. Перенеси остатки по **явно названным** локациям (не «подгоняй» итог
   межскладом).
4. Нормализуй имя мастера.
5. `active=false` на дубле; chatter на обеих.
6. MCP обычно **не умеет** merge — только перенос + архив.

### Когда не сливать

- Разные PN/Ру, IP, материал, ГОСТ, тип соединения.
- Толщина стенки стального отвода расходится **больше 1,0 мм**.
- Цвет клеммы / исполнение N vs PE vs «земля», если это разные SKU учёта.
- Жёсткий бренд в спецификации заказчика (редко) — тогда две карточки
  осознанно.

## Сверка без записи — отчёт

```markdown
| № | Артикул / имя в счёте | Статус | id | Нормализованное имя | Vendor |
|---|----------------------|--------|----|---------------------|--------|
| 1 | … | есть / частично / нет | … | … | есть / обновить / создать |
```

В конце: что создашь при команде «создай», что только обновишь.

## Ответ после записи

Кратко:

- таблица: создано / обновлено / без изменений;
- id карточек и алиасов;
- что намеренно не сливали (IP, PN, …);
- что не делали (закупка, остатки), если логично предложить следующим шагом.

## Чего не делать

- Не создавать карточку «как в счёте» с брендом, если есть нормализованный аналог.
- Не писать бренд в `name` и дублировать его в переводах lang.
- Не менять `list_price`/`standard_price` массово без запроса.
- Не сливать PN/IP «для порядка».
- Не коммитить URL с секретами и пароли в скилл.
- Не создавать материалы с `is_storable=false` без явного указания.

## Связанные скиллы

- Контрагент из счёта → `odoo-supplier-from-invoice` / `odoo-add-partner`.
- Закупка `purchase.order` → `odoo-purchase-from-invoice` (товары — **этот** скилл).
- Парсинг скана → `scanned-invoice-parsing`.
