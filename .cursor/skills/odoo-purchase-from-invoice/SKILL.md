# Odoo: закупка из счёта

Переносимый workflow для складского агента. Работает в любом проекте с Odoo
Purchase/Inventory и MCP. **Не хардкодь** URL базы, id складов, id UoM,
имя MCP-сервера, ИНН «своих» поставщиков — резолви в текущей базе.

Примеры — [examples.md](examples.md).  
Локальные ИНН/форматы счетов — правило в репозитории (если есть).

## Главные правила

- Меняй данные **только** по явной команде: «создай», «оформи», «занеси».
  Вопрос «можешь ли?» — объяснение, без MCP create.
- Один счёт = один `purchase.order`. Не смешивай позиции разных документов.
- Создавай **черновик**. Не подтверждай заказ и не проводи приход, пока
  пользователь этого не попросил.
- **Склад не подставляй по умолчанию.** Нет имени склада в запросе — покажи
  варианты и **жди ответа**. Не создавай PO до выбора.
- Имя MCP-сервера разное: найди сервер Odoo в каталоге MCP, сними схемы
  `search_records` / `create_record` / `get_record` перед вызовами.

## Чеклист

```
- [ ] Явная команда
- [ ] Счёт распознан, суммы сходятся (или пользователь подтвердил расхождение)
- [ ] Дубликат PO по номеру из документа
- [ ] Поставщик по ИНН
- [ ] Склад назван пользователем → in_type_id; иначе спроси
- [ ] Карточки + алиасы (скилл каталога)
- [ ] Qty/цена в UoM карточки (не «как в счёте», если ед.изм. другие)
- [ ] create purchase.order (draft)
- [ ] amount_total ≈ Итого; строк столько же; нужный склад
- [ ] Chatter на PO + отчёт
```

## Что нужно от пользователя

| Данных нет | Действие |
|------------|----------|
| Явная команда | Остановись, не создавай |
| Файл / номер счёта | Спроси источник |
| Склад приёмки | Список складов + 3–6 вероятных, **жди** |
| Полка | Не меняй тип операции, пока не согласился |
| Подтвердить заказ | Только если сказал «подтверди» |

## Шаг 0 — Парсинг

Нужны: номер, дата, ИНН поставщика, таблица (имя, qty, UoM, цена, сумма), итого.

Текстовый PDF / скан / OCR — скиллы парсинга проекта (`scanned-invoice-parsing`
и аналоги). Этот скилл **не** дублирует OCR.

Стоп: `needs_review`, `items_empty`, `sum_mismatch` — покажи расхождение,
**не создавай PO** без отдельного «да, создай». Не подбирай скидку/цену
эвристически.

### Номер счёта (`partner_ref`)

Только **текст документа** («Счет на оплату № …» / «Договор-Счет № …»),
не имя файла и не прошлые заказы.

Пиши **как в источнике**. Не дописывай префикс (`НФ-`, `УТБФ`, `П`), если
его нет в PDF. `origin` = `Счёт <тот же номер>`.

## Шаг 1 — Дубликат

```text
search_records(
  model="purchase.order",
  domain=["|",
    ["partner_ref", "=", "<номер_из_документа>"],
    ["partner_ref", "ilike", "<номер_из_документа>"]],
  fields=["id", "name", "state", "amount_total", "partner_ref",
          "picking_type_id"]
)
```

Нашёл тот же счёт — отдай ссылку, **не создавай второй**.

Пустой черновик того же поставщика **без** этого `partner_ref` — не заполняй
и не удаляй. Упомяни в отчёте.

---

## Шаг 2 — Поставщик

```text
search_records(model="res.partner", domain=[["vat", "=", "<ИНН>"]], ...)
```

Нет записи → скилл `odoo-supplier-from-invoice` (`supplier_rank` ≥ 1).
Без ИНН не создавай контрагента наугад.

---

## Шаг 3 — Склад приёмки

`purchase.order.picking_type_id` = `stock.warehouse.in_type_id`.

```text
search_records(
  model="stock.warehouse",
  domain=[["active", "=", true]],
  fields=["id", "name", "code", "in_type_id"]
)
```

**Склад назван** → ищи по `name` / `code` (`ilike`). Один однозначный —
бери его `in_type_id`. Несколько похожих — уточни.

**Склад не назван** — не угадывай (даже «очевидный» склад металла / основной):

1. Загрузи активные склады.
2. Предложи **3–6 вероятных**: тот, что звучал в этой сессии; склад последних
   PO этого поставщика; склад, имя которого совпадает с типом товара.
3. Спроси выбором (AskQuestion или нумерованный список). Можно указать
   «другой — напишите имя».
4. **Жди ответа.** Дальше (карточки можно готовить) — create PO только после склада.

Полка: не пиши `default_location_dest_id` у `stock.picking.type` без явного
согласия — это меняет приёмку **всего** склада.

## Шаг 4 — Товары

Нормализация, поиск, create карточки и `product.supplierinfo` —
скилл **`odoo-product-catalog`**.

Кратко: код поставщика → типоразмер в `name` → создать только если нет;
сразу алиас (код, торговое имя, цена в UoM карточки). Материалы:
`is_storable=true`. Услуги: `type=service`.

`product_id` в строке PO — id **`product.product`**, не шаблона
(у простых товаров часто совпадает).

### Количество и цена — в UoM карточки

Не хардкодь `product_uom_id` (не «всегда 31»). Бери `uom_id` с варианта.

| В счёте | На карточке | В строке PO |
|---------|-------------|-------------|
| шт. / шт. | шт. | qty и `price_unit` = сумма_строки / qty |
| кг / кг | кг | qty = кг, цена за кг |
| шт. + вес, цена за кг | кг | qty = вес, цена за кг |
| м / м | м | qty = метры |

`price_unit` всегда так, чтобы `qty × price_unit × (1 − discount/100)` =
сумме строки счёта (допуск 0,01).

Нет данных для пересчёта (вес не указан, а карточка в кг) — **спроси**,
не выдумывай.

### Скидка

Если есть «Сумма без скидки» и «Сумма»:

```text
discount = round((1 - sum_after / (qty_card * price_unit)) * 100, 2)
```

где `qty_card * price_unit` — сумма **до** скидки в той же UoM.
Нет колонки скидки — `discount = 0`. Не подгоняй скидку, чтобы закрыть
ошибку OCR.

### Налоги

Цены в счетах часто **с НДС**. Если у товара пустой `supplier_taxes_id`
и в базе нет закупочного НДС — пиши цену как в «сумма с НДС», чтобы
`amount_total` совпал с «Итого».

Если налог на строку навесится сам — либо цена без НДС, либо налоговая
настройка price-included: после create `amount_total` **обязан** совпасть
с итогом. Расхождение → не чини молча, покажи и спроси.

## Шаг 5 — Создать PO

```text
create_record(
  model="purchase.order",
  values={
    "partner_id": <id>,
    "picking_type_id": <in_type_id>,
    "partner_ref": "<номер как в документе>",
    "origin": "Счёт <номер как в документе>",
    "date_order": "<дата счёта> 12:00:00",
    "order_line": [
      [0, 0, {
        "product_id": <product.product id>,
        "product_qty": <qty в UoM карточки>,
        "product_uom_id": <uom_id карточки>,
        "price_unit": <цена в той же UoM>,
        "discount": <0 или из счёта>
      }]
    ]
  }
)
```

Если MCP отверг `product_uom_id` — повтори с `product_uom` (имя поля
зависит от версии). Не ставь налог вручную, если не уверен в поле.

После create: `get_record` шапки + строки. Сразу chatter:

```text
post_message(model="purchase.order", record_id=<id>, subtype="note",
  body="Закупка по счёту <номер> от <дата>, <поставщик>. Итого … . Склад: …")
```

---

## Шаг 6 — Валидация

- Число строк = число позиций таблицы (без рекламы / доставки-в-шапке, если
  её нет отдельной строкой).
- `amount_total` ≈ «Итого» счёта (допуск 0,01). Если в документе отдельно
  «на сумму без НДС» — сверь с `Σ price_subtotal` **и** напиши в отчёте,
  какое поле с чем сравнивал.
- `picking_type_id` — выбранный склад.
- `partner_ref` — номер из документа.

Не прошло — не «докручивай» цены. Покажи факт и спроси.

## Отчёт пользователю

```
✅ Закупка <name> создана
- Счёт: <номер> от <дата>
- Поставщик: <имя>
- Склад: <имя склада>
- Позиций: N
- Сумма: … (как в счёте / поясни UoM)
- Ссылка: <url из MCP, если есть>
```

Таблица: строка счёта → id карточки → qty/UoM в PO → сумма.

Пакет файлов — отдельный блок на каждый. Если какой-то счёт со стоп-флагом —
пропусти его, остальные можно создавать.

## Чего не делать

- Не создавать PO без склада от пользователя.
- Не подтверждать заказ и не делать incoming picking.
- Не брать номер счёта из имени файла.
- Не хардкодить UoM id и `picking_type_id` из другого инстанса.
- Не менять dest-локацию типа поступления «чтобы легло на полку».
- Не заполнять чужой пустой черновик того же поставщика.
- Не коммитить `.env` и URL с секретами в скилл.

## Связанные скиллы

- Парсинг скана / PDF → `scanned-invoice-parsing` (и спец. парсеры поставщика).
- Контрагент → `odoo-supplier-from-invoice` / `odoo-add-partner`.
- Карточки и алиасы → `odoo-product-catalog`.
- Склад, если его ещё нет → `odoo-create-warehouse` (отдельная команда).
