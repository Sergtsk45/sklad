# Task Tracker: миграция складов объектов `ОбМ-*` → `O###`

## Цель

Привести production-склады объектов к новой схеме `object.request.project` → `stock.warehouse` с кодами `O###`, оставив в работе только два реальных объекта:

- `O001` — Ломоносова 164, текущий склад `ОбМ-2`, warehouse id `10`.
- `O002` — Б. Хмельницкого, 112, текущий склад `ОбМ-4`, warehouse id `16`.

Остальные объектные склады считаются тестовыми и должны быть выведены из активной работы:

- `ОбМ-1` — Островского 234.
- `ОбМ-3` — Ленина 231.
- `ОбМ-5` — Северная 165.
- текущие пустые дубли `O001`–`O004`, если они не нужны для production-процессов.

## Принцип миграции

Не переносить остатки между складами. Безопасный путь — сохранить существующие production warehouse id (`10` и `16`), их локации, picking types, quants и связанные документы, а поменять только код, имя и связь с `object.request.project`.

## Риски и ограничения

- Удаление складов в Odoo может быть заблокировано связанными `stock.location`, `stock.move`, `stock.picking`, `purchase.order`, `stock.quant`.
- Для prod предпочтительно архивировать тестовые склады, а не удалять их физически.
- Нельзя переносить quants прямым SQL: остатки должны остаться на существующих локациях или корректироваться штатным складским процессом.
- Legacy aliases `ОбМ-2`/`ОбМ-4` оставлены временно; удалить после переходного периода 2–4 недели.

## Откат

Откат должен быть только через восстановление backup или заранее подготовленный reverse-script, который возвращает:

- warehouse id `10`: `O001` → `ОбМ-2`.
- warehouse id `16`: `O002` → `ОбМ-4`.
- project links и sequence к состоянию до миграции.

Перед production-запуском reverse-script нужно проверить на копии prod.
