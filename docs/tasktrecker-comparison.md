# Tasktracker: Улучшение автосопоставления строк при импорте Excel

## Контекст и цель

**Проблема.** При импорте Excel в требование (`object.request`) автосопоставление товаров работает слабо. На примере файла `Ленина 231 31-000_05-2025-УУТЭ.xlsx` (документ `OR/2026/06/0014`): из 29 строк сопоставлены только 3, причём 2 из них — ложно (короткие имена «Переход», «Бобышка» через `ilike limit=1` взяли первый попавшийся товар из десятков кандидатов).

**Причины (по результатам анализа `excel_parser.py` и данных каталога):**

1. Артикул/обозначение ищется только в `product.supplierinfo.product_code`, который в базе почти пуст. При этом обозначение из Excel часто дословно входит в **название товара** (примеры: «БиТ-63-120-40…», «МТ-100 0-1,6 МПа…», «11б27пм(М)2 Ру16 Ду15 G1/2xG1/2»).
2. Поиск по наименованию — `ilike` всей строки как подстроки: «Кран муфтовый латунный Ду15 В-В» не находит «Кран латунный Ду15 В-В бабочка» из-за одного лишнего слова.
3. Нет нормализации токенов: «Ду15» / «ду 15» / «ДУ-15», «ё»/«е» считаются разными.
4. `limit=1` без оценки уверенности — при множестве кандидатов берётся первый, что порождает тихие ложные сопоставления.

**Цель.** Поднять долю корректных автосопоставлений, исключить ложные совпадения: лучше честный статус «Не сопоставлен», чем неверный товар.

## Принятые решения

| # | Развилка | Решение |
|---|----------|---------|
| 1 | Где искать артикул/обозначение | `product.supplierinfo.product_code` (как сейчас) → затем `product.product.default_code` → затем вхождение в `product.product.name` |
| 2 | Поиск по наименованию | Токенное сопоставление: нормализованные токены имени (+ обозначения) ищутся в названии товара; точный поиск по имени остаётся первым шагом |
| 3 | Порог уверенности | Совпадение принимается, если кандидат единственный или его балл заметно выше остальных; при неоднозначности — `matching_required = True` |
| 4 | Нормализация | Нижний регистр, ё→е, унификация Ду/ДУ-/ду + число, схлопывание пробелов, удаление стоп-токенов (предлоги, «гост» без номера и т.п.) |
| 5 | «Память сопоставлений» через `product.supplierinfo` | Только по **явному действию** пользователя (кнопка «Запомнить сопоставление»), не молча при каждом ручном выборе. Различать **идентификацию** («артикул = этот товар») и **замену** по ситуации (наличие на складе, поставщик) — замены в память не пишутся |
| 6 | Поставщик в «памяти сопоставлений» | Запись supplierinfo создаётся с `partner_id` (если поставщик строки известен); поиск по артикулу сначала пробует пару артикул+поставщик, затем артикул без поставщика |
| 7 | Конфликт в «памяти» (один артикул → разные товары) | Авто-сопоставление **не выполняется** (`matching_required = True`); конфликтующие записи показываются как кандидаты. Никакой перезаписи и недетерминированного `limit=1` |
| 8 | pg_trgm fuzzy-поиск | Вне scope первой итерации; зафиксирован как перспективная задача |

### Этап 5. «Память сопоставлений» (накопление supplierinfo)

Принцип: память хранит только **подтверждённую идентификацию** («этот артикул — это этот товар»), а не ситуативные **замены** (выбор другого товара из-за наличия на складе или поставщика). Поэтому запись создаётся только по явному действию пользователя.

- [x] Серверное действие `action_remember_matching` на `object.request.line` + кнопка «Запомнить сопоставление» в строке (видна снабженцу, активна при заполненных `product_id` и `supplier_article`):
  - создаёт `product.supplierinfo` с `product_code = supplier_article`, `partner_id = preferred_vendor_id` (если задан);
  - если идентичная запись (артикул + товар + поставщик) уже есть — ничего не создаёт, сообщает пользователю;
  - поддержать массовый вызов для выбранных строк (multi-record action).
- [x] Обработка конфликта при создании: если по этому артикулу уже есть запись на **другой** товар — предупредить пользователя (показать существующее сопоставление) и потребовать подтверждение; при подтверждении обе записи остаются, артикул становится «конфликтным» (см. ниже).
- [x] Доработать `match_product_by_article` под конфликты и поставщика:
  - сначала поиск по паре `product_code` + `partner_id` (если поставщик строки распознан из `supplier_raw`);
  - затем по `product_code` без поставщика;
  - если найденные записи указывают на **разные** товары — не сопоставлять (`matching_required = True`), товары-кандидаты передавать в preview как подсказку.
- [x] Защита от мусора: не создавать запись для артикулов из `_SKIP_ARTICLES` и коротких (< 3 символов).
- [x] Тесты:
  - повторный импорт строки после «Запомнить сопоставление» → автоматический match по артикулу;
  - ручной выбор товара **без** нажатия кнопки → supplierinfo НЕ создаётся (замена не запоминается);
  - два разных товара на один артикул (разные поставщики) → match по паре артикул+поставщик, без поставщика — не сопоставляется;
  - конфликт (один артикул → разные товары, поставщик не распознан) → `matching_required = True`, недетерминизма нет.

Примечание: в Odoo 19 поле `product.supplierinfo.partner_id` обязательное, поэтому действие требует `preferred_vendor_id` или первого поставщика товара; без поставщика показывает `UserError` и не создаёт запись.

## Перспективные задачи: накопление знаний из опыта (по мотивам GenericAgent)

Идея self-evolving агента ([lsdefine/GenericAgent](https://github.com/lsdefine/GenericAgent)): не закладывать знания заранее, а «кристаллизовать» их из решённых задач. Этап 5 этого плана («память сопоставлений» с явным подтверждением) — первый шаг в этом направлении. Принцип переноса в ERP: **знание = данные с происхождением** (кто подтвердил, когда, на каком документе); автоматика использует накопленное только при отсутствии конфликтов; никакой молчаливой «самообучаемости».

### П-1. Словарь синонимов и аббревиатур как накапливаемый справочник
- Вынести нормализацию терминов из кода `excel_parser.py` в модель-справочник (`термин → канонический токен`): «ГВФ» → «грязевик фланцевый», «В-В» → «вн/вн» и т.п.
- Пополнение из опыта: при ручном сопоставлении, где запрос и название товара различаются одним «непонятным» токеном, предлагать пользователю «запомнить синоним?» (явное подтверждение, как в этапе 5).
- Эффект: каждое подтверждение улучшает матчинг для всех будущих импортов без изменения кода; словарь — обычные записи Odoo с аудитом (`create_uid`, `create_date`).

### П-2. Профили формата импорта по источникам
- После успешного импорта сохранять «профиль формата»: сигнатура заголовков → маппинг колонок (+ привязка к источнику: проектировщик/поставщик).
- При следующем импорте файл с известной сигнатурой распознаётся мгновенно, без повторного маппинга; новые форматы пополняют коллекцию профилей.

### П-3. Подсказка поставщика из истории решений
- Накапливать статистику ручных выборов `preferred_vendor_id` (в разрезе категории товара / объекта): «для АИТП грязевики обычно LD, краны — Пензапромарматура».
- Использовать только как **подсказку** (предзаполнение с пометкой источника), не как автоматическую подстановку — выбор поставщика ситуативен (цены, наличие, сроки).

### П-4. SOP складских сценариев в `ai_assistant`
- Типовые цепочки операций («требование из файла → расчёт наличия → авто-разбивка → выдача по складам», «приёмка PO с расхождением») хранить как сценарии-знания модуля `ai_assistant` (аналог L3-памяти GenericAgent).
- Пополнение: после прохождения нестандартного кейса с помощью ассистента фиксировать путь решения как новый сценарий (с ручной модерацией перед публикацией).

Анти-паттерн (не переносить): полная автономия агента с самостоятельным изменением окружения/данных — в ERP-контуре обязательны детерминизм, права доступа и аудит.
