# План: поиск товаров v2 (полнотекстовый поиск + синонимы + триграммы)

**Дата:** 2026-10-17
**Статус:** на prod с 2026-10-17 (`decbf8f`, `19.0.2.0.0`)
**Модуль:** `custom_product_search` (до v2 — `19.0.1.1.0`), потребители —
`object_request` (`product_vendor_search.py`), `ai_assistant`
(`ai_search_products`).

## Зачем

Пользователь ищет «болт 16» в списке товаров и видит 3 карточки из 10
подходящих: остальные записаны «Болт М16×70», а не «Болт 16х 70». Это не
частный случай, а свойство механизма: поиск сравнивает подстроки, а каждое
новое разночтение закрывается очередной регуляркой.

## Как устроено сейчас

1. **`x_search_name`** — stored computed поле на `product.template` и
   `product.product`: lower, `ё→е`, NBSP, `ду 50→ду50`, `х/×→x`, `,→.` между
   цифрами (`product_search_utils.normalize_product_search_text`).
2. **`name_search`** (только Many2one-автокомплит): сначала стандартный
   `ilike` Odoo; если он вернул меньше лимита — добор по
   `x_search_name ilike <нормализованная строка>`, AND по словам, артикулу
   поставщика. Порядок — `_order` модели, релевантности нет.
3. **`pg_trgm` GIN** на `x_search_name` — только ускоряет `ilike`, функции
   сходства не используются.
4. **`ai_search_products`** — то же + обрезка русских окончаний, если точный
   поиск пуст.

### Слабые места

| # | Проблема | Пример |
|---|----------|--------|
| W1 | Не участвует в поиске списков, фильтрах, отчётах | «Склад → Товары», «болт 16» → 3 из 10 |
| W2 | Правила — регулярки в коде; нет данных-синонимов | «М16» ≠ «16», «оцинк» ≠ «оцинкованный», «шаровой» ≠ «шаровый» |
| W3 | Stored-поле не пересчитывается при смене правил | у 623, 126 в индексе до 2026-10-17 оставалось «16х 70» |
| W4 | Нет ранжирования; лимит 8 обрезает нужное | стандартные `ilike`-попадания всегда выше |
| W5 | Подстрока, а не токен; опечатки не прощаются | «16» находит «160»; «болд м16» → 0 |
| W6 | Все слова запроса обязательны | «труба ППР 63(ХВС) 4м» → 0: «4м» нет в имени |

| Режим | Полный текст строки: в топ-8 | на 1-м месте | Первые 2 слова: в топ-8 |
|-------|-----------------|------------|-------------------|
| A. Список товаров (стандартный `ilike`) | 9 (2%) | 6 (2%) | 67 (18%) |
| B. Автокомплит, как на prod | 30 (8%) | 14 (4%) | 151 (40%) |

Прототип D — 30 строк Python, без синонимов и без весов; это оценка

модели «все подстроки обязательны» на «токены + ранжирование», а не новые
регулярки.

## Предлагаемый механизм

Всё внутри PostgreSQL: без нового сервиса, права Odoo сохраняются (поиск
возвращает id, дальше обычный `search`/`read` с record rules).

### 1. Токенизация (детерминированная, в Python)

`tokenize_product_name(name) -> list[str]`:

- нормализация как сейчас (lower, `ё`, пробелы, `×/х/x`);
- разбиение на буквенные и числовые токены с сохранением составных:
  `М16×70` → `м16`, `м`, `16`, `70`, `16x70`; `Ду50` → `ду50`, `ду`, `50`;
  `57х3,5` → `57`, `3.5`, `57x3.5`;
- стоп-токены единиц: `мм`, `шт`, `м` (как отдельное слово).

Хранение: `x_search_tokens` (`tsvector`, конфигурация `simple`), stored,
пересчёт через `@api.depends('name', 'default_code', seller_ids...)`.

### 2. Синонимы — данные, а не код

Модель `product.search.synonym` (`term`, `canonical`, `active`), правится
в UI снабженцем. При индексации и разборе запроса токен заменяется на
каноническую форму:

| term | canonical |
|------|-----------|
| оцинк, оц, цинк | оцинкованный |
| dn | ду |
| pn | ру |
| шаровой | шаровый |
| ппр, pp-r | ппр |

Русские словоформы — словарь `russian` (snowball) для словарных слов
(`шаровый/шаровой/шаровых`); числа и коды — через `simple`.

### 3. Запрос и ранжирование

```sql
SELECT id,
       ts_rank_cd(x_search_tokens, q) * 2
     + word_similarity(:raw, x_search_name) AS score
FROM product_product, to_tsquery('simple', :prefix_or_query) q
WHERE x_search_tokens @@ q            -- OR по токенам, а не AND
   OR :raw <% x_search_name           -- pg_trgm: опечатки
ORDER BY score DESC
LIMIT :limit;
```

- токены запроса объединяются через OR с префиксом (`болт:* | м16:*`), ранг
  — по доле совпавших токенов (как прототип D) и `ts_rank_cd`;
- `word_similarity` / оператор `<%` (`pg_trgm`) — опечатки («болд»);
- GIN-индексы: `x_search_tokens` (tsvector) и существующий trgm.

### 4. Одна точка входа для всех UI

- `product.product._search_product_ids(query, limit, domain)` — единственный
  метод, возвращает упорядоченные id.
- `name_search` / `web_name_search` (автокомплит, включая `object_request`
  и поиск по прайсу поставщика) — через него.
- **Список товаров**: в search view `product.template` / `product.product`
  поле поиска «Товар» получает `filter_domain` на новое поле с
  `_search`-методом (`x_smart_search`), который вызывает тот же механизм.
  Порядок в списке — стандартный; фильтрация — по новому механизму.
- `ai_search_products` — тот же метод, морфология-фолбэк уходит.

### 5. Пересчёт и миграция

- Версия правил токенизации (`TOKENIZER_VERSION`) хранится в
  `ir.config_parameter`; при её смене `post_migrate` пересчитывает весь
  каталог (1,5 тыс. карточек — секунды). Это закрывает W3 навсегда.
- Синонимы: изменение записи → пересчёт затронутых карточек
  (`x_search_name ilike term`).

## Реализация (2026-10-17): отличия от дизайна

- **Морфология — усечение до 5 букв в Python**, а не словарь `russian`:
  в образе нет `snowballstemmer`, а одинаковый код в модели и в бенчмарке
  важнее. Снаружи разница не видна: `шаровый/шаровой/шаровых` → `шаров`.
- **Хранение — `Char` с токенами через пробел.** GIN-индекс по выражению
  `array_to_tsvector(string_to_array(x_search_tokens, ' '))`, запрос —
  OR точных лексем (`'a' | 'b'`). Префиксы и опечатки раскрываются заранее
  по словарю каталога (кэш в процессе), поэтому `pg_trgm` /
  `word_similarity` в запросе не нужны. Ранжирование (IDF, доля веса
  запроса, покрытие имени, совпадение первого слова) — в Python по ≤ 2000
  кандидатам.
- **Метод — `_smart_search_ids`** на миксине `product.search.mixin`; он
  общий для шаблона и варианта.
- **Наружный диаметр стальной трубы → Ду** (`76×3,5` → `ду65`); так
  нашлись фитинги без явного «Ду».
- **AI строже автокомплита.** `invoice_context_helper` автоматически
  сопоставляет единственный результат, поэтому слова, которых нет в
  каталоге, не отбрасываются: должны совпасть все. `exact` — без
  нечёткости, `morphology` — с опечатками. Широкое ранжирование работает
  только там, где выбирает человек (автокомплит, список).
- **Фильтр списка**: найдены все известные слова **или** ≥ 80% веса запроса.
- **Итог на копии prod** (376 пар): автокомплит — 92% в топ-8 и 53% на
  1-м месте (до v2 — 9% / 5%); фильтр списка по 2 словам — 73% (до v2 — 19%);
  ~6 мс на запрос, 100–200 мс на 50 тыс. товаров.

## Риски

- **Ранжирование OR по токенам** даёт «шум» внизу списка — допустимо для
  автокомплита (8 строк), но в списке товаров фильтр должен оставаться
  строгим: там нужна доля совпавших токенов ≥ порога (например, все
  значимые токены, кроме единиц).
- `web_name_search` в `object_request` уже переопределён (прайс поставщика,
  OBR-038) — встраивать, а не заменять.
- `pg_trgm` есть; словарь `russian` встроен в PostgreSQL 15 — новых
  расширений не нужно.
- Производительность: 1,5 тыс. карточек — не проблема; проверить на 50 тыс.
  синтетикой.
