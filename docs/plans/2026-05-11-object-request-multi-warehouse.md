# Plan: Multi-warehouse выдача для object.request

**Создан:** 2026-05-11
**Оркестрация:** orch-2026-05-11-10-15-multi-warehouse
**Статус:** 🟢 Готов к выполнению
**Цель:** Перенести управление складами из шапки требования на уровень строк, автоматизировать расчёт и распределение запасов по всем складам компании и перестроить выдачи/закупки под multi-warehouse поток.
**Всего задач:** 10
**Оценка времени:** 2–3 итерации разработки + миграция.

---

## Контекст и ограничения
- Поле `warehouse_id` на `object.request` удаляется — прораб больше не выбирает склад.
- Остатки считаются по всем активным складам компании; распределение хранится в новой модели `object.request.line.stock`.
- Объект (`object.request.project`) обязан иметь собственный склад с кодом `O###`, создаваемый автоматически и недоступный для переименования.
- Wizard выдачи должен формировать по одному `stock.picking` на склад, а закупка принимает товары на склад объекта.
- Прораб видит только агрегаты по строке; детальное распределение доступно снабженцу/администратору.

## Зависимости высокого уровня
1. Создание склада на объекте (MW-01) необходимо до этапов с закупкой и выдачей.
2. Удаление поля склада из требования (MW-02) должно произойти до переработки действий и вьюх.
3. Новая модель распределения (MW-03) и расчёт остатков (MW-04) — база для авто-разбивки, wizard'ов и миграций.
4. Обновление UI/ACL (MW-08) опирается на новые модели и действия.
5. Миграции и тесты (MW-09) закрывают все предыдущие этапы.

## Детализация задач

### MW-01: Склад и код на уровне объекта
- **Приоритет:** Critical · **Сложность:** Moderate · **Зависимости:** нет
- Автогенерация `code` через sequence `object.request.project.code` (`O001`, `O002`, …).
- `create()` объекта создаёт `stock.warehouse` с именем «{name} склад», кодом объекта и привязкой к компании.
- `warehouse_id` хранится на объекте, read-only, активность синхронизируется с объектом, `unlink` запрещён при остатках или заявках.
- `write()` блокирует изменение `name`/`code` (кроме админов/ sudo) и синхронизирует имя склада.
- Тесты: автосоздание, запрет переименования, каскадная архивация, защита от удаления с остатками.

### MW-02: Чистка шапки требования
- **Приоритет:** Critical · **Сложность:** High · **Зависимости:** MW-01
- Удалить `warehouse_id`, `check_warehouse_ids`, `stock_check_confirmed` из модели, views, wizard импорта.
- Обновить security/record rules, чтобы поля не ожидались в ACL.
- Переписать `action_check_stock`, `action_auto_split`, `action_open_issue_wizard`, `action_open_purchase_wizard` под новый поток.
- UI: скрыть поля склада, обновить формы/листы.

### MW-03: Модель `object.request.line.stock`
- **Приоритет:** Critical · **Сложность:** High · **Зависимости:** MW-02
- Создать модель `(line_id, warehouse_id, qty_available, qty_free, qty_to_issue, qty_reserved, manual_override, last_check_date)`.
- One2many `stock_ids` на строке, compute/store агрегатов `qty_available_total`, `qty_to_issue_total`, `qty_to_buy_total` и т. д.
- ACL: доступ на редактирование только снабженцам/админам; прораб видит только агрегаты.

### MW-04: Расчёт остатков по всем складам
- **Приоритет:** High · **Сложность:** High · **Зависимости:** MW-03
- Сервис на модели строки, который подтягивает `free_qty` из `stock.quant` по всем активным складам компании (batched `read_group`).
- Заполняет / обновляет `stock_ids` с `qty_available` и `qty_free`, сбрасывает `qty_to_issue` если нет override.
- Wizard `stock_check_wizard` превращается в подтверждение только для прораба, который видит итоговые числа.

### MW-05: Авто-разбивка и массовые действия
- **Приоритет:** High · **Сложность:** Moderate · **Зависимости:** MW-04
- Алгоритм минимизации числа складов: сначала склад, где хватает, иначе сортировка по убыванию `qty_free`.
- Массовые кнопки «Выдать максимум», «Закупить всё», «Сбросить разбивку» c подтверждением при наличии ручных override.
- Поле `manual_plan_override` на строке сигнализирует о ручной правке.

### MW-06: Wizard выдачи (multi-picking)
- **Приоритет:** High · **Сложность:** High · **Зависимости:** MW-05
- Предпросмотр: группировка строк по складу (`stock_ids`), настройка даты/комментария на группу, возможность отключить склад.
- Подтверждение создаёт по одному `stock.picking` на склад, движения берут `qty_to_issue` по конкретному `stock_id`.
- Резервы (`qty_reserved`) обновляются по каждой строке/складу, учитывая `free_qty`.

### MW-07: Wizard закупки
- **Приоритет:** Medium · **Сложность:** Moderate · **Зависимости:** MW-01, MW-05
- Использует `project_id.warehouse_id` как склад приёмки PO (через `picking_type_id`/`dest_location_id`).
- Позволяет принудительно отправить строки «на закупку», даже если есть остаток (через ручную правку `stock_ids`).

### MW-08: UI и безопасность
- **Приоритет:** Medium · **Сложность:** Moderate · **Зависимости:** MW-03..MW-07
- Новая вкладка/вложенный список «Размещение по складам» (видна снабженцу).
- Прораб видит только агрегаты; скрываем `stock_ids` через ACL/view modifiers.
- Обновить действия, smart-buttons, chatter сообщения (например, уведомления при полной обеспеченности).

### MW-09: Миграции и тесты
- **Приоритет:** Critical · **Сложность:** High · **Зависимости:** MW-01..MW-08
- pre-migrate: snapshot существующих требований/объектов, создать недостающие склады, перенести значения `warehouse_id` в распределение.
- post-migrate: прогнать расчёт остатков и авто-разбивку для legacy данных (или пометить для ручного обзора).
- Обновить существующие тесты (OBR-011, 012, 017, 020, 024, 025) и добавить новые для line stock, wizardов, миграций.

### MW-10: Документация
- **Приоритет:** Medium · **Сложность:** Moderate · **Зависимости:** MW-01..MW-09
- Обновить `docs/datamodelspecobjectrequest.md`, `docs/functionalspecobjectrequest.md`, `docs/project.md` (mermaid-схема потока), `docs/tasktracker.md`.
- Добавить запись в `docs/changelog.md`, ссылку на новую архитектуру в `docs/roadmapobjectrequest.md`.
