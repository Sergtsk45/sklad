# План: AI-консультант для Odoo 19 через OpenRouter

**Дата:** 2026-03-15  
**Статус:** Подготовлено к реализации  
**Сценарий:** встроенный чат в правом нижнем углу, история только в сессии браузера, ответы на основе документации Odoo  
**Цель:** дать пользователю нативного AI-помощника внутри Odoo, который объясняет возможности системы, подсказывает пошаговые действия и отвечает с учетом текущего экрана и прав пользователя.

## 1. Цель и границы

### Что нужно сделать

Создать кастомный Odoo-модуль `ai_assistant`, который:

- показывает кнопку/виджет чата в правом нижнем углу;
- открывает компактное окно диалога поверх интерфейса Odoo;
- хранит историю сообщений только в памяти браузерной сессии;
- отправляет вопросы на backend Odoo;
- backend проксирует запрос в OpenRouter;
- модель отвечает, опираясь на документацию Odoo и контекст текущего интерфейса;
- помощник подсказывает:
  - как пользоваться модулями;
  - где находятся функции;
  - какие есть возможности;
  - как выполнить действие в текущем разделе.

### Что не входит в первую версию

- сохранение истории в БД Odoo;
- обучение модели на пользовательских данных компании;
- исполнение действий от имени пользователя;
- автозаполнение документов без подтверждения;
- глубокая интеграция с бизнес-данными (например, советы по конкретным сделкам);
- голосовой ввод, файлы, изображения, RAG по вложениям.

## 2. Рекомендуемая архитектура

Архитектура должна быть разделена по слоям:

1. **Presentation Layer**
   - OWL-компонент чата;
   - systray launcher или floating widget;
   - session storage в браузере.
2. **Application Layer**
   - frontend service для отправки сообщений;
   - backend controller `/ai_assistant/chat`;
   - formatter для нормализации контекста и ответа.
3. **Domain Layer**
   - prompt builder;
   - policy layer для ограничений ответа;
   - context resolver (какой модуль/экран открыт).
4. **Infrastructure Layer**
   - OpenRouter client;
   - config reader;
   - knowledge provider для документации Odoo.

Это соответствует принципам SRP и separation of concerns: UI не знает про OpenRouter, controller не знает про реализацию интерфейса, prompt builder не зависит от OWL.

## 4. UI/UX дизайн первой версии

### Размещение

- плавающая кнопка в правом нижнем углу;
- при нажатии открывается chat panel поверх текущего экрана;
- окно не должно ломать стандартные формы Odoo;
- на мобильном/узком экране превращается в full-width bottom sheet.

### Состав интерфейса

- header:
  - название: `AI-консультант`
  - индикатор статуса: `онлайн / ошибка`
  - кнопка очистки текущей сессии
- body:
  - сообщения пользователя;
  - ответы ассистента;
  - блок suggested prompts;
  - состояние загрузки (`печатает...`)
- footer:
  - textarea;
  - кнопка отправки;
  - подсказка о пределах ответственности ассистента.

### Базовые prompt suggestions

- `Как пользоваться этим разделом?`
- `Что можно делать на этой странице?`
- `Как добавить товар на склад?`
- `Как создать контрагента?`
- `Какие возможности есть в этом модуле?`

## 5. Где и как хранить историю

Поскольку ты указал, что истории в БД не нужно, рекомендуемый вариант:

- хранить сообщения в `sessionStorage`;
- ключ формата: `odoo_ai_assistant_session_v1`;
- очищать историю:
  - по кнопке `Очистить`;
  - при logout;
  - при ошибке несовместимой версии схемы.

### Почему `sessionStorage`, а не `localStorage`

- история исчезает после завершения сессии браузера;
- меньше риск накопления старых чувствительных данных;
- соответствует твоему требованию "достаточно только в сессии браузера".

## 6. Источник знаний: документация Odoo

### Цель knowledge layer

Ассистент не должен отвечать только “из общих знаний”. Он должен опираться на:

- официальную документацию Odoo;
- справку по установленным модулям;
- локальный контекст интерфейса.

### Практический подход для MVP

Рекомендую двухуровневую схему:

1. **Статическая база знаний**
   - заранее подготовленный набор документов по Odoo 19:
     - Inventory
     - CRM
     - Contacts
     - Sales
     - Purchase
     - Settings / navigation basics
   - хранить как markdown/json snippets внутри модуля или рядом в `docs/knowledge/`.

2. **Контекстный prompt injection**
   - перед вызовом OpenRouter backend подбирает релевантные фрагменты по текущему модулю и вопросу;
   - затем вставляет их в system/developer prompt.

### Что рекомендую НЕ делать в первой версии

- полноценный vector DB;
- Elasticsearch/pgvector;
- индексацию всех help-страниц Odoo;
- онлайн web-scraping при каждом запросе.

Для MVP достаточно curated knowledge pack. Это быстрее, дешевле и предсказуемее.

## 7. Контекст, который должен видеть ассистент

Минимальный контекст первого релиза:

- текущий app/module:
  - `crm`, `sale`, `purchase`, `stock`, `contacts`, `settings`
- текущий action/menu label;
- текущая модель (`res.partner`, `sale.order`, `stock.picking` и т.д.);
- тип экрана:
  - list
  - form
  - kanban
  - dashboard
- язык пользователя;
- имя пользователя и группы доступа;
- URL/action hash.

### Пример полезного контекста

```json
{
  "module": "stock",
  "action_name": "Products",
  "model": "product.template",
  "view_type": "list",
  "user_lang": "ru_RU",
  "user_groups": ["stock.group_stock_user"]
}
```

### Зачем это нужно

Тогда ассистент сможет отвечать не абстрактно, а так:

- “Вы сейчас в модуле Склад, на списке товаров”
- “Чтобы добавить новый товар, нажмите Создать”
- “Если кнопки нет, проверьте права доступа или перейдите в Продукты”

## 8. Backend API дизайн

### HTTP endpoint

Рекомендуемый endpoint:

- `POST /ai_assistant/chat`

### Входной payload

```json
{
  "message": "Как добавить товар на склад?",
  "context": {
    "module": "stock",
    "model": "product.template",
    "view_type": "list",
    "action_name": "Products"
  },
  "history": [
    {"role": "user", "content": "..." },
    {"role": "assistant", "content": "..." }
  ]
}
```

### Выходной payload

```json
{
  "answer": "Пошаговая инструкция...",
  "suggestions": [
    "Показать путь через меню",
    "Как оприходовать остатки?",
    "Чем товар отличается от услуги?"
  ],
  "meta": {
    "model": "openrouter/...",
    "sources": ["inventory_basics", "products_guide"],
    "context_used": true
  }
}
```

## 9. Сервис OpenRouter

### Что должно быть в конфиге

Нужно хранить:

- API key OpenRouter;
- base URL;
- имя модели;
- таймаут;
- максимальную длину history;
- feature flag включения модуля.

### Где хранить

Лучший путь для Odoo:

- системные параметры `ir.config_parameter`;
- UI в `Settings` для администратора;
- ключ не должен попадать в frontend.

### Важные ограничения

- frontend никогда не должен напрямую вызывать OpenRouter;
- все запросы только через backend Odoo;
- ключ логировать нельзя;
- ошибки OpenRouter нужно возвращать в безопасной форме.

## 10. Prompt strategy

### Базовый system prompt

Роль ассистента:

- ты встроенный помощник по Odoo 19;
- отвечаешь только по использованию интерфейса и возможностям системы;
- не выдумываешь кнопки, поля, пути меню;
- если не уверен — так и пишешь;
- приоритет у переданного контекста и knowledge snippets.

### Формула промпта

1. System prompt
2. Правила безопасности
3. Контекст экрана
4. Релевантные фрагменты документации
5. Последние N сообщений истории
6. Текущий вопрос пользователя

### Стиль ответа

- короткие пошаговые инструкции;
- термины Odoo на языке интерфейса;
- без технического шума;
- при необходимости 2-3 варианта;
- если функционал недоступен — предложить, где его включить.

## 11. Knowledge provider для документации Odoo

### MVP-реализация

Создать curated mapping:

- `stock` → snippets по товарам, остаткам, инвентаризации, перемещениям
- `purchase` → snippets по заказам поставщикам и приемке
- `sale_management` → snippets по котировкам, заказам, счетам
- `crm` → snippets по лидам, воронке, активностям
- `contacts` → snippets по контрагентам и контактам

### Подход к поиску

Сначала простой retrieval:

1. определить модуль по текущему context;
2. выбрать его knowledge pack;
3. сделать keyword matching по вопросу;
4. взять top 3-5 фрагментов;
5. передать в prompt.

### Почему это достаточно для первой версии

- предсказуемое поведение;
- меньше токенов;
- легче дебажить;
- проще обновлять knowledge base вручную.

## 12. Безопасность

### Риски

- утечка OpenRouter API key;
- попадание конфиденциальных полей в prompt;
- prompt injection от пользователя;
- советы по функциям, к которым у пользователя нет доступа.

### Меры защиты

1. backend whitelist полей контекста:
   - модуль
   - action
   - model
   - view type
   - lang
   - user group ids/names
2. не отправлять:
   - содержимое документов;
   - персональные данные клиентов;
   - цены/финансы;
   - токены/секреты;
   - email body/attachments
3. response guard:
   - фильтр на небезопасные инструкции;
   - запрет на обещание автоматических действий;
   - отказ от советов вне доступных модулей.

## 13. Производительность

### Ограничения MVP

- один запрос чата = один HTTP roundtrip;
- без streaming в первой версии можно стартовать быстрее;
- history ограничить последними 10-12 сообщениями;
- knowledge snippets ограничить по размеру.

### Что можно добавить позже

- streaming token-by-token;
- response caching для частых вопросов;
- precomputed hints по модулю;
- rate limiting по пользователю.

## 14. Права доступа

### Минимальная модель доступа

- использовать `auth='user'` для controller;
- доступ только авторизованным пользователям;
- отдельная security group:
  - `AI Assistant User`
  - `AI Assistant Admin`

### Для администратора

Нужно дать экран настроек:

- включить/выключить модуль;
- выбрать модель OpenRouter;
- задать system prompt override;
- включить debug logging;
- ограничить доступ по группам.

## 17. Риски и компромиссы

### Риск 1. Ответы будут слишком общими

**Причина:** мало контекста или слабая knowledge base.  
**Снижение риска:** curated docs pack + screen context + примеры хороших ответов.

### Риск 2. Ассистент будет советовать несуществующие кнопки

**Причина:** LLM hallucination.  
**Снижение риска:** жесткий prompt, knowledge snippets, requirement “если не уверен — скажи об этом”.

### Риск 3. Утечка чувствительных данных

**Причина:** слишком богатый payload в prompt.  
**Снижение риска:** whitelist контекста, никаких содержимых записей и документов.

### Риск 4. Сложность поддержки frontend в Odoo 19

**Причина:** OWL/assets/hook points Odoo.  
**Снижение риска:** начать с минимального floating widget, не встраиваться глубоко в каждый экран.

## 18. Критерии готовности MVP

- чат открывается из правого нижнего угла;
- работает во всех нужных модулях;
- история хранится только в сессии браузера;
- OpenRouter key хранится только на backend;
- ассистент отвечает по-русски;
- ассистент учитывает текущий модуль/экран;
- ассистент отвечает на основе документации Odoo;
- есть fallback-сообщение при ошибке API;
- нет хранения диалогов в БД;
- модуль ставится и обновляется стандартным способом Odoo.

## 19. Рекомендация по старту реализации

Начинать нужно не с OpenRouter, а с каркаса UI и backend proxy:

1. каркас модуля и floating widget;
2. session history;
3. controller с mock answer;
4. реальный OpenRouter client;
5. knowledge layer;
6. admin settings;
7. security hardening.

Такой порядок снижает риск и упрощает отладку.
