# Tasktracker OBR-039: статус строки «Ожидает счёт от поставщика»

**Дата:** 2026-08-12  
**Уточнения:** 2026-08-13  
**Статус:** Реализовано локально (`19.0.1.10.12`); ручная UI-приёмка под ролями — у заказчика  
**Модуль:** `custom_addons/object_request`  
**Приоритет:** Средний  
**Назначение документа:** готовое техническое задание для агента-исполнителя

## Контекст и цель

Снабженцу нужен ручной способ отметить строку требования, по которой поставщик
уже выбран, счёт у него запрошен, но ещё не получен. Товар в каталоге Odoo
может отсутствовать: счёт выписывают по наименованию требования, а поставщик
подбирает позицию из своей базы. Сопоставление номенклатуры в этом случае
завершают позже, когда счёт придёт.

После установки галочки строка должна:

- получить статус **«Ожидает счёт от поставщика»**;
- подсвечиваться стандартным синим цветом Odoo (`decoration-info`);
- оставаться видимой и доступной в существующих процессах комплектации;
- возвращаться к обычному вычисляемому статусу после снятия галочки.

На первом этапе реализуется только ручная отметка. Будущая команда
**«Запросить счёт»** должна использовать то же поле, поэтому бизнес-факт и
вычисляемый статус необходимо разделить.

## Границы MVP

- [x] Boolean-поле ручной отметки **«Счёт запрошен»**.
- [x] Новый вычисляемый статус строки

- [x] Синяя подсветка badge и всей строки во всех актуальных списках.

- [x] Серверная защита прав, не ограниченная только XML-представлением.
- [x] Проверка обязательного поставщика перед установкой галочки; товар и
  завершённое сопоставление не обязательны.
- [x] Автоматический сброс отметки при замене уже заданного поставщика или
  товара (по каждой строке recordset); первое заполнение пустого поля
  отметку не снимает.
- [x] Фильтр строк **«Ожидает счёт»**.
- [x] Автоматические, регрессионные и ручные проверки.
- [x] Обновление версии модуля и проектной документации.

### Не входит в MVP

- Не создавать кнопку или действие **«Запросить счёт»**.
- Не отправлять письма и сообщения поставщику.
- Не создавать документ запроса счёта, вложение или activity.
- Не сохранять дату, автора, канал и историю запроса счёта.
- Не распознавать получение счёта автоматически.
- Не блокировать подготовку закупки или создание черновика PO.
- Не блокировать резервирование и выдачу складской части строки.
- Не менять `qty_to_buy`, `qty_to_issue`, `procurement_mode` и остатки.
- Не добавлять новый счётчик в шапку требования.

Пункты раздела «Не входит в MVP» являются зафиксированными ограничениями, а
не незавершёнными работами. Расширение автоматизации оформляется отдельной
задачей после появления процесса **«Запросить счёт»**.

## Принятые проектные решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | Хранить факт в Boolean `supplier_invoice_requested` | Будущая кнопка сможет установить тот же признак без переделки статуса |
| 2 | Назвать checkbox «Счёт запрошен» | Это совершившийся факт; «Ожидает счёт» остаётся производным статусом |
| 3 | Добавить `awaiting_supplier_invoice` в `line_state` | Статус участвует в стандартном badge, фильтрах и группировке Odoo |
| 4 | Использовать `decoration-info` | Это штатный синий/голубой цвет Odoo без отдельного CSS |
| 5 | Явное изменение checkbox — снабженец; helper как у соседних действий допускает `base.group_system` | Это не замена ACL: пользователь только с Settings не получит write на строку. Тест «админ обслуживает поле» — superuser или снабженец+`group_system`, не Settings без роли модуля |
| 6 | Требовать выбранного поставщика; товар и завершённое сопоставление не обязательны | Счёт часто запрашивают по `name_raw`, пока нужного товара нет в каталоге |
| 7 | Не требовать `qty_to_buy > 0` | Снабженец может запросить счёт до авторазбивки или ручного заполнения плана |
| 8 | Сбрасывать отметку только при замене уже заданного поставщика или товара | «Фактическая смена» = старый ID был задан и новый отличается (включая очистку). Первое заполнение пустого `product_id` или `preferred_vendor_id` отметку не снимает |
| 9 | Не снимать отметку при авторазбивке, пересчёте остатка или изменении количеств | Эти операции не меняют адресата запроса счёта |
| 10 | В MVP не блокировать закупку и выдачу | Новый статус пока информационный; изменение маршрута закупки требует отдельного бизнес-решения |
| 11 | Полное обеспечение (`qty_issued >= qty_requested`) и отмена имеют приоритет над ожиданием счёта | Завершённая или отменённая строка не должна оставаться синей |
| 12 | Ожидание счёта имеет приоритет над `requires_mapping` | Иначе отмеченная несопоставленная строка останется красной, фильтр «Ожидает счёт» её не найдёт, а снабженец не увидит рабочий этап ожидания |
| 13 | Кладовщик в общей editable-таблице колонку checkbox не видит | Поле с `groups="object_request.group_supply_manager"` скрывается, не становится readonly; достаточно синего badge |
| 14 | Менять галочку только во встроенной таблице формы требования | Standalone list сейчас не editable и без form view; inline-edit туда не добавлять |
| 15 | `approval_state` не влияет на галочку | Документ на согласовании остаётся `draft`; запрос счёта в этот момент допустим |
| 16 | Исключить awaiting из `decoration-danger` и `decoration-warning` во всех трёх списках | Иначе `matching_required=True` оставит строку красной поверх синего |
| 17 | Сброс в `write()` считать по каждой строке recordset отдельно | Массовая запись одного ID не должна снимать отметку у строк, где значение не изменилось |
| 18 | Фильтр «Только проблемные» исключает ожидающие счёт строки | Иначе search view разойдётся со счётчиком и smart-button |

```python

```

- [x] Добавить `supplier_invoice_requested` в `@api.depends` метода

- [x] Реализовать следующий приоритет расчёта. Если checkbox снят, семантика
  существующих статусов должна совпасть с текущим `_compute_line_state()`.
  Полное обеспечение проверять как `qty_issued >= qty_requested`, а не по
  текущему `line_state`.

| Приоритет | Условие | `line_state` | Отображение |
|---:|---|---|---|
| 1 | `is_cancelled` | `cancelled` | Нейтральное |
| 2 | Нет товара или `matching_required`, **и** checkbox снят | `requires_mapping` | Красное |
| 3 | `qty_issued >= qty_requested` | `fully_supplied` | Зелёное |
| 4 | `supplier_invoice_requested` | `awaiting_supplier_invoice` | Синее |
| 5 | `qty_issued > 0` | `partially_issued` | Жёлтое/оранжевое |
| 6 | Товар выбран | `ready` | Нейтральное |
| 7 | Иначе | `draft` | Нейтральное |

Эквивалентная логика:

```python
if line.is_cancelled:
    line.line_state = "cancelled"
elif (
    (not line.product_id or line.matching_required)
    and not line.supplier_invoice_requested
):
    line.line_state = "requires_mapping"
elif line.qty_issued >= line.qty_requested:
    line.line_state = "fully_supplied"
elif line.supplier_invoice_requested:
    line.line_state = "awaiting_supplier_invoice"
elif line.qty_issued > 0:
    line.line_state = "partially_issued"
elif line.product_id:
    line.line_state = "ready"
else:
    line.line_state = "draft"
```

- [x] Проверить, что строка без товара / с `matching_required=True` и
  установленным checkbox становится синей, а не красной.
- [x] Проверить, что после снятия checkbox такая строка снова
  `requires_mapping`.
- [x] Проверить, что отмеченная частично обеспеченная mixed-строка становится
  синей: это означает, что складская часть может выдаваться, а по закупочной
  части ожидается счёт.
- [x] Проверить, что полностью обеспеченная строка становится зелёной даже
  при оставшейся ручной отметке.
- [x] Не менять существующую семантику остальных значений `line_state`, когда
  checkbox снят.

### Автоматический сброс при изменении контекста запроса

Единое правило для товара и поставщика: **сбрасывать только замену уже
заданного значения**. Первое заполнение пустого поля отметку не снимает.

| Было | Стало | Сброс |
|---|---|---|
| поставщик A | поставщик B | да |
| поставщик A | пусто | да |
| пусто | поставщик A | нет |
| поставщик A | тот же A | нет |
| товар A | товар B | да |
| товар A | пусто | да |
| пусто | товар A | нет |
| товар A | тот же A | нет |

- [x] В `write()` оценивать **каждую строку recordset отдельно**. Нельзя
  записать `supplier_invoice_requested=False` на весь recordset, если часть
  строк получила тот же ID, что уже был, или первое заполнение пустого поля.
- [x] Пример: `lines.write({"product_id": X})` — сбросить checkbox только у
  строк, где старый `product_id` был задан и отличался от X. Строки с пустым
  товаром и строки, где товар уже был X, сохранить отметку.
- [x] То же правило для `preferred_vendor_id`.
- [x] Не сбрасывать отметку при изменении UoM, количеств, размещения,
  комментария, остатков, `matching_required` / `matching_source` без смены
  товара/поставщика, или плана закупки/выдачи.
- [x] Добавить `onchange`, чтобы checkbox очищался в форме немедленно при
  замене/очистке уже выбранного поставщика или товара. Первое назначение
  пустого поля в onchange отметку не очищает.
- [x] В `_onchange_product_id` сброс при очистке товара делать **до**
  текущего раннего `return`, если `not self.product_id`.
- [x] Автоподстановка первого поставщика после выбора товара попадает в
  ветку «пусто → значение» и отметку не снимает. Если поставщик уже был и
  его ID меняется — сбросить.
- [x] Серверный `write()` должен оставаться источником истины для импорта,
  RPC, массовых действий и будущей автоматизации.
- [x] Аккуратно разделить явную пользовательскую попытку изменения checkbox и
  внутренний автоматический сброс. Прораб/кладовщик не должны получать ошибку
  прав, если их допустимая замена товара/поставщика автоматически очищает
  старую отметку.
- [x] Если в том же `write()` переданы новый товар/поставщик и
  `supplier_invoice_requested=True`: автосброс не выполнять; разрешить только
  снабженцу; валидировать уже новые значения (поставщик обязателен, товар
  нет) и сохранить `True`. Правило действует и для recordset.

## Риски и контроль

| Риск | Контроль |
|---|---|
| Несопоставленная отмеченная строка останется красной | `requires_mapping` только если checkbox снят; `decoration-danger` и `decoration-warning` исключают awaiting во всех трёх списках |
| Синий статус скроет полное обеспечение | `fully_supplied` (`qty_issued >= qty_requested`) выше ожидания счёта |
| Жёлтая или красная decoration перебьёт синюю | Исключить awaiting из danger и warning на `<list>` и на badge |
| Прораб/кладовщик изменят поле через RPC | Серверная group-проверка в create/write поверх неизменных ACL |
| Пользователь только с Settings обойдёт проверку поля | Helper `group_system` не заменяет ACL; тест не использовать Settings без роли модуля |
| После замены поставщика останется старый запрос счёта | Серверный сброс плюс onchange; первое заполнение пустого вендора не сбрасывает |
| Первое проставление товара снимет отметку | Сбрасывать product только при замене/очистке уже выбранного ID |
| Массовый write снимет отметку у неизменённых строк | Считать каждую строку recordset отдельно; покрыть тестом |
| Авторазбивка случайно снимет отметку | Сбрасывать только при замене уже заданного вендора или товара |
| Новый статус неожиданно заблокирует PO или выдачу | В MVP не добавлять status-фильтры в purchase/issue workflow; закрепить регрессионными тестами |
| Ожидание счёта станет «проблемной строкой» | Исключить `supplier_invoice_requested` из counter, smart-button и фильтра «Только проблемные»; `_requires_nomenclature_review` не трогать |
| Пользователь примет checkbox за подтверждение получения счёта | Название «Счёт запрошен» и tooltip должны явно описывать запрос, не получение |
| Поле останется отмеченным после создания PO | Это сознательное ограничение MVP; автоматический lifecycle вынести в будущую задачу |
| Новая колонка сбросит пользовательский layout | Ожидаемо: ключ localStorage включает набор полей; JS не мигрировать |
| Агент затронет несвязанные пользовательские изменения | Проверить dirty worktree, применять точечные patch и не выполнять reset/checkout |
