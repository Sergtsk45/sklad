# Tasktracker: сохранение настроек колонок в таблицах строк требования

## Задача: object_request — сохранение ширины, порядка и набора колонок таблиц строк
- **Статус**: Реализована 2026-07-08, ревью проведено и баг с потерей позиции скрытых колонок при drag исправлен в тот же день; автоматические проверки пройдены, ручной UI test plan ожидает прогона в браузере.
- **Дата создания**: 2026-07-07
- **Описание**: Реализовать сохранение пользовательской ширины, порядка и набора колонок для таблиц строк требования на комплектацию: встроенной таблицы во вкладке **«Строки»**, отдельного списка по smart-button **«Строки»**, списка по smart-button **«Проблем»** и списка строк, открываемого после **«Диагностика PO»**. Встроенная таблица сейчас отображается стандартным Odoo `<list>` в поле `line_ids` с классом `o_object_request_line_ids`; отдельные списки используют list-view модели `object.request.line`. Ручной resize колонок в Odoo работает только в рамках текущего рендера, пользовательский порядок колонок не поддерживается, а настройка набора optional-колонок должна быть независимой для каждого пользовательского сценария.
- **Цель**: После изменения ширины, порядка или видимости колонок пользователь должен видеть ту же раскладку при повторном открытии соответствующей таблицы или обновлении страницы. Настройки встроенной таблицы требования, списка **«Строки»**, списка **«Проблем»** и диагностического списка PO должны храниться независимо друг от друга.
- **Границы задачи**:
 - Не менять бизнес-модели `object.request` и `object.request.line`.
 - Не менять данные строк требования и порядок строк по `sequence`.
 - Не влиять на другие list-view таблицы Odoo, включая общие списки `object.request.line` вне сценариев требования.
 - Использовать точечное frontend-расширение модуля `object_request`.

## Контекст

- Основная таблица товаров: `custom_addons/object_request/views/object_request_views.xml`, поле `line_ids`, CSS-класс `o_object_request_line_ids`.
- Отдельный список строк: `custom_addons/object_request/views/object_request_line_views.xml`, action `action_open_lines()`.
- Отдельный список проблемных строк: `custom_addons/object_request/views/object_request_line_views.xml`, action `action_open_problem_lines()`.
- Диагностический сценарий PO: smart-button **«Диагностика PO»**, action `action_check_purchase_stock_matches()`, который работает со строками `object.request.line`.
- Существующий resize Odoo: `odoo/addons/web/static/src/views/list/column_width_hook.js`.
- Существующее сохранение optional-колонок Odoo: `odoo/addons/web/static/src/views/list/list_renderer.js`, `localStorage`.
- Рекомендуемое хранение для MVP: `browser.localStorage`, отдельно для текущего пользователя и браузера.

## Риски и контроль

- **Риск:** patch `ListRenderer` затронет другие списки Odoo.
  **Контроль:** включать логику только при наличии `.o_object_request_line_ids` для встроенной таблицы или при явном распознавании action/context сценария строк требования.

- **Риск:** настройки разных списков строк требования начнут перетирать друг друга.
  **Контроль:** хранить независимый `layoutScope` в ключе `localStorage`: встроенная таблица, smart-button «Строки», smart-button «Проблем», диагностика PO.

- **Риск:** drag заголовков конфликтует с сортировкой колонок.
  **Контроль:** разделить pointer-сценарии drag, resize и click-sort; не запускать сортировку после фактического drag.

- **Риск:** drag колонок конфликтует с drag строк через `sequence`.
  **Контроль:** использовать разные handle/selector: заголовки `thead th[data-name]` для колонок и штатный `.o_handle_cell` для строк.

- **Риск:** сохранённые настройки устареют после изменения XML-колонок.
  **Контроль:** применять только известные активные колонки, новые колонки добавлять в XML-порядке, неизвестные игнорировать.

- **Риск:** `localStorage` не синхронизируется между браузерами и рабочими местами.
  **Контроль:** явно считать это ограничением MVP; server-side хранение вынести в отдельную задачу при необходимости.
