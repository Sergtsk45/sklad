## TD-001: Ограничение доступа MCP к моделям Odoo (least privilege)

- **Статус**: открыто
- **Контекст**: при проверке подключения MCP (`list_models`) зафиксирован режим **YOLO / FULL ACCESS** — инструментам доступен широкий перечень моделей без явного белого списка и с полными операциями read/write/create/unlink. Это ускоряет разработку и автоматизацию, но **повышает риск** утечки данных, случайных массовых изменений и злоупотребления при компрометации сессии Cursor/ключа.
- **Цель**: привести конфигурацию Odoo + `mcp-server-odoo` к **принципу минимально достаточных прав** (least privilege) по отраслевой практике для API-интеграций.

### Рекомендуемые направления (лучшие практики)

1. **Отключить YOLO** в продакшене (переменные окружения / флаги сервера MCP — см. документацию `mcp-server-odoo`). Оставить явный список разрешённых моделей и операций.
2. **Белый список моделей**: включать только то, что нужно сценариям (например `res.partner`, при необходимости `account.move` / строки — по факту процессов); не экспортировать `ir.*`, `res.users`, платежи и пр. без необходимости.
3. **Разделение ролей**: отдельный технический пользователь Odoo с узкими группами прав + отдельная БД/API-key только для MCP; не использовать учётку администратора.
4. **Операции по умолчанию «только чтение»** там, где не нужны create/write/unlink; повышать уровень точечно под задачи (например импорт поставщиков).
5. **Согласование с бизнесом**: зафиксировать, какие сущности может менять агент автоматически, что только после явного подтверждения в чате (см. также `.cursor/rules/agent-intent-odoo-mcp.mdc`).
6. **Аудит**: периодически пересматривать список моделей в MCP и журналы действий в Odoo (кто и что менял через API).

### Критерии готовности (Definition of Done)

- [ ] YOLO отключён на целевом окружении или обоснованно ограничён только dev/stage.
- [ ] Задокументирован и применён белый список моделей и разрешённых операций.
- [ ] Для MCP используется выделенный пользователь Odoo с минимальными группами.
- [ ] В `docs/project.md` (или здесь) кратко зафиксирована актуальная политика доступа.

### Ссылки

- Конфигурация MCP: `~/.cursor/mcp.json`, переменные `ODOO_*`.
- Правила агента: `.cursor/rules/agent-intent-odoo-mcp.mdc`.

## TD-002: Единицы измерения труб (метр / m) и приход на склад в метрах при закупке в кг/тоннах

- **Статус**: открыто
- **Контекст**: для номенклатуры труб (категория **Трубы**, ID карточек 581–602) в Odoo заведена отдельная единица **«метр»** (UoM ID 32), при этом в системе уже есть стандартная **«m»** (ID 9). Дублирование единиц без настройки категории UoM и коэффициентов пересчёта мешает закупкам, складу и отчётам. Поставщики металлопроката (например счета в **кг**, оплата/отгрузка в **тоннах**) отличаются от учётной единицы на складе (**метры**).
- **Цель**: единая понятная модель UoM для труб и автоматическое (или полуавтоматическое) попадание количества на склад **в метрах** при оформлении прихода/оплаты в **кг** или **тоннах**.

### Подзадачи

#### 1. Разобраться с единицами измерения «метр» и «m»

- Сравнить **«метр»** (ID 32) и **«m»** (ID 9): категория UoM, коэффициенты, где уже используются.
- Принять решение: **одна** единица длины для труб (рекомендуется оставить одну, вторую архивировать или связать через категорию «Длина / Length»).
- Привести карточки категории **Трубы** (581–602) и закупочные UoM к выбранному варианту.
- Задокументировать правило именования UoM для новых товаров-труб.

#### 2. Правило или скрипт: приход/оплата в кг или тоннах → склад в метрах

- Описать бизнес-формулу пересчёта: **кг → м** через вес 1 м (из ГОСТ/паспорта/прайса) или **т → м** через теоретическую массу погонного метра по размеру трубы.
- Варианты реализации (выбрать после анализа):
  - **Odoo**: вторичная UoM на `product.template`, автоматизация (Automated Action), серверное действие при `stock.picking` / `purchase.order.line`, кастомный модуль `product.template` (поле «кг/м» или «м/т»).
  - **Вне Odoo**: скрипт/скилл при разборе счёта (MCP) с подстановкой количества в метрах в строку прихода.
- Учесть: разная длина хлыста (L=6 м / L=12 м), оцинковка vs чёрная (разный вес), округление, допуск на счёте поставщика в **кг**.
- Согласовать момент пересчёта: при **создании заказа поставщику**, при **приёмке** или при **проведении счёта**.

### Критерии готовности (Definition of Done)

- [ ] В справочнике UoM нет конфликтующих дублей «метр»/«m» для одной категории товаров; политика зафиксирована в документации.
- [ ] Все трубы (581–602 и новые) используют согласованную единицу длины и при необходимости — закупочную UoM (кг/т) с корректным коэффициентом.
- [ ] Реализован и протестирован сценарий: строка закупки/прихода в **кг** или **т** → количество на складе в **м** (хотя бы для одной тестовой позиции ВГП и одной э/с).
- [ ] Описана инструкция для пользователя склада/закупок (когда пересчёт срабатывает сам, когда нужно ввести «кг/м» в карточке товара).

### Ссылки

- Карточки труб: `product.template` ID 581–602, категория **Трубы** (ID 14).
- UoM: «метр» ID 32, «m» ID 9, «kg» ID 16, «Ton» ID 17.
- Скилл счетов/поставщиков: `.cursor/skills/odoo-supplier-from-invoice/SKILL.md` (может дополняться расчётом метража).

## TD-005: Vision-fallback парсинга счетов через существующий OpenRouterClient

- **Статус**: открыто
- **Контекст**: при внедрении приёмки товаров из счёта (этап **V3-10**, [`roadmap_ai_assistant_v3_invoice.md`](roadmap_ai_assistant_v3_invoice.md)) принято решение **D1** — парсить счета внутри Odoo (порт text-first логики `invoice-extractor`: pdfplumber + эвристики). В исходном сервисе `extraction_specific_PDF` для сложных/сканированных PDF был **Vision-fallback** через отдельный LLM-вызов (`llm_client.call_vision_llm`, рендер страниц в изображения PyMuPDF). При портировании в Odoo этот fallback **намеренно отложен** (text-first MVP в AIA-055), иначе пришлось бы тянуть тяжёлые зависимости (PyMuPDF/Pillow) и дублировать LLM-клиент.
- **Синергия**: в модуле `ai_assistant` **уже есть** `services/openrouter_client.py` с поддержкой vision (используется для скриншотов экрана, см. AIA-024/025). Vision-fallback для счетов-сканов можно реализовать **через этот же клиент**, без отдельного LLM-сервиса и без сетевой зависимости от `invoice-extractor`: text-first (pdfplumber) → при пустом/некачественном результате рендер страницы в изображение → vision-запрос через существующий `OpenRouterClient` → нормализация тем же `services/invoice_parsing/normalizer.py`.
- **Цель**: единый путь извлечения данных из счёта (текст + скан) внутри Odoo, переиспользующий существующий vision-клиент и нормализатор, без внешнего сервиса.

### Подзадачи

1. Детектор «нужен ли vision»: text-first дал 0 позиций / провалил арифметическую валидацию (`validate_invoice_data`) → триггер fallback.
2. Рендер PDF-страницы в изображение: оценить зависимость (PyMuPDF `fitz` или `pdf2image`+poppler) и объявить как `external_dependencies` только при включении fallback.
3. Vision-запрос через существующий `OpenRouterClient` (vision-модель из `ir.config_parameter ai_assistant.vision_model`), промпт — портировать `VISION_PROMPT` из `invoice-extractor/extractor.py`.
4. Нормализация результата тем же `normalizer.py` (общий формат с text-first), повторная валидация.
5. Rate-limit/размер: переиспользовать существующие лимиты vision-запросов чата (`_VISION_RATE`).
6. Тесты: фикстура «скан без текстового слоя» → fallback вызывается; мок vision-клиента.

### Критерии готовности (Definition of Done)

- [ ] Скан-PDF без текстового слоя распознаётся через `OpenRouterClient` vision, результат в общем формате.
- [ ] Нет отдельного LLM-клиента/сервиса для счетов — переиспользован существующий.
- [ ] Тяжёлые зависимости рендера объявлены и подключаются только при включённом fallback.
- [ ] Покрыто тестом с мок-vision; text-first остаётся путём по умолчанию.

### Ссылки

## TD-006: Неверное извлечение итога «к оплате» в счетах поставщика (формат Метиз Комплект / 1С)

- **Статус**: открыто
- **Контекст**: при загрузке счёта **`ЗаказПокупателя_ООО_«ДВ_Партнёр»_МК000051249_10_06_2026.pdf`** (поставщик **ООО «Метиз Комплект»**, № **МК000051249**) ассистент распознал **3 позиции**, но в сводке указал сумму **14 560,00 ₽** вместо ожидаемой **17 185,57 ₽** (итого с НДС). Валидация выдала предупреждение:

  > Итого без НДС (14560.00) + НДС (2625.57) = 17185.57 ≠ к оплате (14560.00)

  То есть в `totals.total_w_vat` попала сумма **без НДС**, хотя НДС извлечён корректно. Риск: неверная сумма в чате, при создании PO и сверке со счётом в 1С.
- **Гипотеза**: в `_parse_totals` (`extractor.py`) поле `total_wo_vat` берётся по первому совпадению `итого[:\s]+…`, а `total_w_vat` — только по шаблону `всего к оплате`. У счетов из 1С (шапка «Заказ покупателя») подписи итогов могут отличаться («Итого», «Всего», «К оплате», «Итого к оплате» и т.п.); при отсутствии строки «Всего к оплате» в `total_w_vat` может оказаться та же цифра, что и в промежуточном «Итого», либо первая строка «Итого» перехватывается раньше финальной суммы с НДС.
- **Цель**: корректно различать **сумму без НДС**, **НДС** и **итого к оплате (с НДС)** для типовых форматов счетов поставщиков (в т.ч. Метиз Комплект / 1С).

### Подзадачи

1. Сохранить PDF как тестовую фикстуру (или зафиксировать извлечённый текст/pdfplumber-таблицы) и воспроизвести расхождение в `test_invoice_parsing.py`.
2. Разобрать разметку итогового блока в документе: какие подписи и в каком порядке идут на последней странице / в подвале таблицы.
3. Доработать `_parse_totals`: приоритет финальной суммы к оплате; синонимы (`итого к оплате`, `всего`, `к оплате`); не путать промежуточное «Итого» в таблице с итогом документа; при необходимости — вывод итогов из последней строки таблицы или арифметика `total_wo_vat + vat_total` как fallback с пометкой в warnings.
4. Убедиться, что сводка в `chat_controller` (`upload_invoice`) показывает **total_w_vat** (к оплате), а не промежуточное «Итого без НДС».
5. Регрессия: счёт **УТ-1132** / **НФ-504** (существующие тесты) остаётся зелёным.

### Критерии готовности (Definition of Done)

- [ ] Для `МК000051249` (или эквивалентной фикстуры): `totals.total_w_vat` = **17 185,57**, предупреждение о расхождении НДС/к оплате **отсутствует**.
- [ ] Покрыто unit-тестом на извлечение итогов (text-first).
- [ ] В `docs/changelog.md` зафиксировано исправление.

### Ссылки

- Парсер: `custom_addons/ai_assistant/services/invoice_parsing/extractor.py` (`_parse_totals`, `_TOTAL_RE`, `_TOPAY_RE`).
- Валидация: `custom_addons/ai_assistant/services/invoice_parsing/validators.py`.
- Референс-счёт (корректный парсинг): тесты с **УТ-1132** — `tests/test_invoice_parsing.py`.

## TD-007: Превью изображения товара при наведении в выпадающем списке «Товар» (требование на комплектацию)

- **Статус**: открыто

## TD-009: Подтверждаемое обновление закупочной цены из счёта

- **Статус**: открыто
- **Контекст**: после сопоставления строки счёта с существующим товаром
  `ai_assistant` использует найденную запись
  `product.supplierinfo` для конкретного поставщика. Сейчас расхождение между
  ценой в счёте и сохранённой закупочной ценой поставщика не превращается в
  явное предложение обновить карточку и не формирует понятную историю
  изменения.
- **Цель**: если цена строки счёта отличается от действующей цены в
  `product.supplierinfo` того же поставщика, ассистент должен показать старую
  и новую цену и запросить разрешение на обновление. Без подтверждения данные
  Odoo не изменяются. После подтверждения обновляется закупочная цена
  поставщика, а в карточке товара фиксируется заметка с историей изменения.

### Бизнес-правила

1. Сравнивать цену только с записью `product.supplierinfo`, соответствующей:
   - найденному товару;
   - поставщику из текущего счёта;
   - той же валюте, единице измерения и применимому порогу `min_qty`.
2. Не сравнивать цену счёта с `product.template.list_price`: это продажная
   цена, а не закупочная цена поставщика.
3. Приводить цену к сопоставимому виду до сравнения:
   - учитывать валюту и единицу измерения;
   - явно определить, включает ли цена НДС;
   - использовать округление валюты, а не прямое сравнение float.
4. Не запрашивать обновление при разнице в пределах допустимого округления.
   Порог должен быть конфигурируемым; базовый вариант — точность валюты.
5. При нескольких подходящих `supplierinfo` не выбирать первую запись
   автоматически: показать конфликт и потребовать ручного выбора.
6. Каждое обновление должно быть идемпотентным: повторная обработка того же
   счёта не создаёт повторную заметку и не меняет цену повторно.
7. Обновление разрешено только пользователю с группой снабжения и проходит
   через существующий механизм pending action / подтверждения ассистента.

### Предлагаемый UX

Ассистент показывает карточку подтверждения:

```text
Обновить закупочную цену?
Товар: Переход канализационный наружный эксцентрический ПП Ду160×110
Поставщик: ООО ТД Центр Снабжения
Текущая цена: 250,00 ₽/шт.
Цена в счёте: 269,24 ₽/шт.
Изменение: +19,24 ₽ (+7,70%)
Счёт: УТБФ0006395 от 06.08.2026

[Обновить цену] [Оставить текущую]
```

При отказе цена не изменяется; решение можно записать в audit без заметки в
карточке товара.

### История и заметка

После подтверждения:

- обновить `product.supplierinfo.price`;
- сохранить дату начала новой цены в `date_start`, если это согласуется с
  текущей политикой прайс-листов;
- вызвать `message_post()` на `product.template` и записать:
  - поставщика;
  - старую и новую цену;
  - валюту и единицу измерения;
  - абсолютное и процентное изменение;
  - номер и дату счёта;
  - дату/время обновления;
  - пользователя, подтвердившего обновление;
  - ссылку на `product.supplierinfo` и, если доступно, вложение счёта.

Текст заметки не должен содержать банковских реквизитов, токенов или других
секретов. Если chatter на карточке товара недостаточен для отчётности,
рассмотреть отдельную модель истории цен вместо перезаписи заметок.

### Подзадачи

1. Добавить сервис сравнения закупочных цен с нормализацией валюты, UoM, НДС
   и округления.
2. Расширить `InvoiceContextHelper`: возвращать `price_status`,
   `supplierinfo_id`, старую/новую цену и рассчитанную разницу.
3. Добавить read-only preview и pending action
   `update_supplier_price_from_invoice`; LLM не должен вызывать `write()`
   напрямую.
4. Реализовать write-tool с повторной проверкой старой цены непосредственно
   перед записью (защита от конкурентного изменения).
5. После успешного `write()` публиковать структурированную заметку в chatter
   товара и запись в `ai.assistant.audit`.
6. Обработать сценарии: новая запись `supplierinfo`, несколько прайс-линий,

7. Добавить настройку порога расхождения и возможность полностью отключить
   предложения обновления цены.
8. Обновить документацию пользователя, `docs/project.md`,

### Критерии готовности (Definition of Done)

## TD-011: Production-hardening многошаговых workflow AI-ассистента

- **Статус**: открыто
- **Краткое описание фичи**: replenishment и moving используют structured LLM
  только для текстовых параметров, а детерминированные workflow выполняют
  поиск записей, расчёты, state transitions и создание одного draft PO или
  internal picking после явной кнопки.
- **Контекст**: replenishment уже работает в `ai_assistant`, а moving реализуется
  по тому же session/state-machine контракту. Ниже перечислены улучшения
  надёжности и сопровождения перед масштабированием на несколько workers и
  более сложные закупочные и складские сценарии. `ReplenishmentSessionStore` и
  `MovingSessionStore` являются
  process-local: токен может быть не виден другому worker, а локальный lock не
  обеспечивает распределённый execute-once.
- **Цель**: сделать workflow устойчивым в multi-worker production, удобным для
  исправления ранее введённых данных и полностью покрытым автоматизированными
  acceptance-тестами.

### Подзадачи

1. **Общее хранилище сессий и блокировок**: заменить process-local
   workflow stores на общую DB/Redis-backed реализацию с TTL и атомарным
   `execute once`, чтобы любой Odoo worker видел токен и два параллельных клика
   не могли создать два PO или два picking.
2. **Возврат к предыдущим шагам**: использовать поле `correction` extractor-а
   и добавить явные действия «Изменить товар/количество/поставщика/склад» с
   корректными переходами state-machine и повторным расчётом плана.
3. **Parent/child-поставщики**: формально определить, считается ли коммерческая
   семья одним вариантом или дочерние контакты показываются отдельно; проверить
   валюту PO, vendor-строки и дедупликацию для обоих вариантов.
4. **Расширить backend acceptance-покрытие**: несколько поставщиков,
   variant/date/min_qty, ACL без Supply, совместимые и несовместимые UoM,
   округление упаковок, parent/child и разные валюты, истёкший токен,
   недопустимые состояния PO и конкурентный Execute.
5. **Добавить HttpCase и QUnit/tour**: маршрутизация invoice/replenishment/moving,
   LLM-timeout fallback, восстановление токена после reload, lifecycle
   ResultCard, очистка active-token и вызовы `actionService.doAction()` для
   composer/report.
6. **Наблюдаемость и аудит**: структурированные события старта/завершения,
   fallback LLM, истечения сессии, повторного подтверждения изменившейся цены и
   ошибок PO-действий; метрики без текстов запросов, цен и токенов.
7. **Стандартная JSON Schema в runtime**: унифицировать сборку образа так,
   чтобы всегда использовался поддерживаемый `jsonschema`; локальный subset
   validator оставить только как аварийный fallback и покрыть parity-тестами.

### Критерии готовности (Definition of Done)

- [ ] Сессия продолжается после попадания запроса на другой Odoo worker.
- [ ] Конкурентный Execute в разных workers создаёт ровно один PO или picking.

  нельзя оценить, сколько позиций ещё не закрыто обеспечением (выдача +
  закупка). Счётчик полностью обеспеченных строк
  (`line_fully_supplied_count`) на модели уже есть, но в list view не
  выводится; отдельного поля «необеспеченных» нет.
- **Цель**: в списке требований показывать **количество необеспеченных
  позиций**, чтобы снабженец/прораб видел остаток работы без открытия
  каждого документа.

### Определение «необеспеченной» позиции

Согласовать с правилом закрытия документа (`action_close`): строка
необеспечена, если `line_state not in ('fully_supplied', 'cancelled')`.
То есть:

- полностью обеспеченные (`qty_issued >= qty_requested`) **не** считаются;
- отменённые **не** считаются;
- частично выданные, к закупке, без номенклатуры, «ожидает счёт» —
  **считаются**.

Не путать с `line_problem_count` (проблемы сопоставления/поставщика/остатка)
и с `line_to_buy_count` (только план закупки).

### Рекомендуемая реализация

1. Stored computed Integer на `object.request`, например
   `line_unsupplied_count` (string **«Необеспеченных»**), в том же
   `_compute_line_counters`, зависимость от `line_ids.line_state`.
2. Колонка в `view_object_request_list` рядом со «Строк» /
   «Несопоставленных»; `decoration-warning` при значении `> 0`;
   `optional="show"`.
3. По желанию: smart-button / клик открывает строки с domain
   `line_state not in ('fully_supplied', 'cancelled')` (аналог
   `action_open_problem_lines`).
4. Тесты: 0 при всех `fully_supplied`/`cancelled`; считает частичные и
   awaiting; обновляется после выдачи/закупки.

- [ ] Число совпадает с `len(line_ids)` без `fully_supplied` и `cancelled`.
- [ ] Есть focused-тесты на compute и присутствие поля в list XML.

## TD-013: Запрет редактирования колонки «Наименование» после статуса «В работе»

- **Статус**: открыто
- **Контекст**: в требовании на комплектацию (`object.request`) состав строк
  уже блокируется после выхода из черновика: нельзя добавлять/удалять строки
  и менять `qty_requested` (`_is_composition_locked`,
  `_check_qty_requested_change`, `readonly` на «Запрошено»). Колонка
  **«Наименование (файл)»** (`name_raw`) при этом остаётся редактируемой
  в статусе **«В работе»** (`in_progress`) — и в editable-таблице формы
  (снабженец/кладовщик), и в автономном списке строк. Это позволяет
  переписать исходное наименование из Excel после того, как документ уже
  запущен в работу (сопоставление, выдача, закупка).
- **Цель**: после перехода документа в **«В работе»** колонка
  «Наименование» должна быть только для чтения. Правка `name_raw`
  разрешена только в статусе **«Черновик»** (`draft`).

### Рекомендуемая реализация

1. UI: `readonly="parent.state != 'draft'"` на `name_raw` в
   `object_request_views.xml` (таблица `line_ids` снабженца/кладовщика;
   при необходимости — форма прораба). В автономном списке строк
   (`object_request_line_views.xml`) — `readonly="request_id.state != 'draft'"`
   или эквивалент.
2. Сервер: в `object.request.line.write` запретить изменение `name_raw`,
   если `request_id.state != 'draft'` (тот же принцип, что у
   `qty_requested`). XML-readonly недостаточно: обход через RPC/MCP.
3. Не блокировать остальные рабочие поля в `in_progress`: товар,
   поставщик, план выдачи/закупки, «счёт запрошен», размещение.
4. Тесты: `write({'name_raw': ...})` в `draft` проходит; в `in_progress`
   — `UserError`; UI-архитектура содержит readonly. Регрессия существующих
   тестов composition lock (`test_obr015_state_machine.py`).

### Критерии готовности (Definition of Done)

- [ ] В статусе «В работе» колонка «Наименование» не редактируется в форме
  требования и в списке строк.
- [ ] Сервер отклоняет изменение `name_raw` вне `draft`.
- [ ] В черновике наименование по-прежнему можно править.
- [ ] Focused-тесты + кратко в `docs/changelog.md` после внедрения.
