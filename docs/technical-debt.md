# Технический долг

Реестр известных компромиссов и долгосрочных улучшений по проекту «Одоо» (Cursor + MCP + инстанс Odoo). Статусы: **открыто**, **в работе**, **закрыто** (с датой и ссылкой на решение при необходимости).

---

## TD-001: Ограничение доступа MCP к моделям Odoo (least privilege)

- **Статус**: открыто
- **Контекст**: при проверке подключения MCP (`list_models`) зафиксирован режим **YOLO / FULL ACCESS** — инструментам доступен широкий перечень моделей без явного белого списка и с полными операциями read/write/create/unlink. Это ускоряет разработку и автоматизацию, но **повышает риск** утечки данных, случайных массовых изменений и злоупотребления при компрометации сессии Cursor/ключа.
- **Цель**: привести конфигурацию Odoo + `mcp-server-odoo` к **принципу минимально достаточных прав** (least privilege) по отраслевой практике для API-интеграций.

### Рекомендуемые направления (лучшие практики)

1. **Отключить YOLO** в продакшене (переменные окружения / флаги сервера MCP — см. документацию `mcp-server-odoo`). Оставить явный список разрешённых моделей и операций.
2. **Белый список моделей**: включать только то, что нужно сценариям (например `res.partner`, при необходимости `account.move` / строки — по факту процессов); не экспортировать `ir.*`, `res.users`, платежи и пр. без необходимости.
3. **Разделение ролей**: отдельный технический пользователь Odoo с узкими группами прав + отдельная БД/API-key только для MCP; не использовать учётку администратора.
4. **Операции по умолчанию «только чтение»** там, где не нужны create/write/unlink; повышать уровень точечно под задачи (например импорт поставщиков).
5. **Согласование с бизнесом**: зафиксировать, какие сущности может менять агент автоматически, что только после явного подтверждения в чате (см. также `.cursor/rules/agent-intent-odoo-mcp.mdc`).
6. **Аудит**: периодически пересматривать список моделей в MCP и журналы действий в Odoo (кто и что менял через API).

### Критерии готовности (Definition of Done)

- [ ] YOLO отключён на целевом окружении или обоснованно ограничён только dev/stage.
- [ ] Задокументирован и применён белый список моделей и разрешённых операций.
- [ ] Для MCP используется выделенный пользователь Odoo с минимальными группами.
- [ ] В `docs/project.md` (или здесь) кратко зафиксирована актуальная политика доступа.

### Ссылки

- Конфигурация MCP: `~/.cursor/mcp.json`, переменные `ODOO_*`.
- Правила агента: `.cursor/rules/agent-intent-odoo-mcp.mdc`.

## TD-002: Единицы измерения труб (метр / m) и приход на склад в метрах при закупке в кг/тоннах

- **Статус**: открыто
- **Контекст**: для номенклатуры труб (категория **Трубы**, ID карточек 581–602) в Odoo заведена отдельная единица **«метр»** (UoM ID 32), при этом в системе уже есть стандартная **«m»** (ID 9). Дублирование единиц без настройки категории UoM и коэффициентов пересчёта мешает закупкам, складу и отчётам. Поставщики металлопроката (например счета в **кг**, оплата/отгрузка в **тоннах**) отличаются от учётной единицы на складе (**метры**).
- **Цель**: единая понятная модель UoM для труб и автоматическое (или полуавтоматическое) попадание количества на склад **в метрах** при оформлении прихода/оплаты в **кг** или **тоннах**.

### Подзадачи

#### 1. Разобраться с единицами измерения «метр» и «m»

- Сравнить **«метр»** (ID 32) и **«m»** (ID 9): категория UoM, коэффициенты, где уже используются.
- Принять решение: **одна** единица длины для труб (рекомендуется оставить одну, вторую архивировать или связать через категорию «Длина / Length»).
- Привести карточки категории **Трубы** (581–602) и закупочные UoM к выбранному варианту.
- Задокументировать правило именования UoM для новых товаров-труб.

#### 2. Правило или скрипт: приход/оплата в кг или тоннах → склад в метрах

- Описать бизнес-формулу пересчёта: **кг → м** через вес 1 м (из ГОСТ/паспорта/прайса) или **т → м** через теоретическую массу погонного метра по размеру трубы.
- Варианты реализации (выбрать после анализа):
  - **Odoo**: вторичная UoM на `product.template`, автоматизация (Automated Action), серверное действие при `stock.picking` / `purchase.order.line`, кастомный модуль `product.template` (поле «кг/м» или «м/т»).
  - **Вне Odoo**: скрипт/скилл при разборе счёта (MCP) с подстановкой количества в метрах в строку прихода.
- Учесть: разная длина хлыста (L=6 м / L=12 м), оцинковка vs чёрная (разный вес), округление, допуск на счёте поставщика в **кг**.
- Согласовать момент пересчёта: при **создании заказа поставщику**, при **приёмке** или при **проведении счёта**.

### Критерии готовности (Definition of Done)

- [ ] В справочнике UoM нет конфликтующих дублей «метр»/«m» для одной категории товаров; политика зафиксирована в документации.
- [ ] Все трубы (581–602 и новые) используют согласованную единицу длины и при необходимости — закупочную UoM (кг/т) с корректным коэффициентом.
- [ ] Реализован и протестирован сценарий: строка закупки/прихода в **кг** или **т** → количество на складе в **м** (хотя бы для одной тестовой позиции ВГП и одной э/с).
- [ ] Описана инструкция для пользователя склада/закупок (когда пересчёт срабатывает сам, когда нужно ввести «кг/м» в карточке товара).

### Ссылки

- Карточки труб: `product.template` ID 581–602, категория **Трубы** (ID 14).
- UoM: «метр» ID 32, «m» ID 9, «kg» ID 16, «Ton» ID 17.
- Скилл счетов/поставщиков: `.cursor/skills/odoo-supplier-from-invoice/SKILL.md` (может дополняться расчётом метража).

## TD-003: API + validate + связка OR → PO → склад объекта

- **Статус**: открыто
- **Контекст**: целевой процесс снабжения (прораб → OR, снабженец → PO / internal → остатки на **ОбМ-***) описан в [`docs/instruction-warehouse-supply-cycle.md`](instruction-warehouse-supply-cycle.md). Оплата — в **1С**; инвентаризация для прихода закупки **не используется**. При попытке провести приход **ОбМ-4/IN/00001** через MCP (смена `state` без `button_validate`) остатки **не создались**; обход через инвентаризацию противоречит процессу. В базе уже есть связка OR→PO (`origin`: OR/2026/05/0002 → P00008), но PO может создаваться на **неверный склад** (Офис вместо объекта), если не задан `picking_type_id` склада назначения.
- **Цель**: замкнуть цикл **OR → PO (или INT) → Validate → quants на ОбМ-N** с возможностью автоматизации через API/MCP **без** инвентаризации и **без** vendor bill.

### Примечание (2026-05-23)

Подзадачу **1** (validate / confirm через API) можно закрыть **без кастомного модуля Odoo**: в `mcp-server-odoo` v0.6.0 уже есть инструмент **`call_model_method`** (обёртка над XML-RPC `execute_kw`). Он регистрируется при двух условиях: `ODOO_YOLO=true` **и** `ODOO_MCP_ENABLE_METHOD_CALLS=true` в env MCP (`~/.cursor/mcp.json`); после изменения конфига — **перезапуск MCP** в Cursor. Вызовы: `purchase.order.button_confirm`, `stock.picking.button_validate` с `arguments=[[record_id]]`. Согласовать с **TD-001** (отдельный пользователь, не `admin`).

### Подзадачи

#### 1. Server-side validate / confirm для MCP

- Включить **`call_model_method`** в MCP (см. примечание выше) или добавить вызов **`purchase.order.button_confirm`** и **`stock.picking.button_validate`** через XML-RPC / расширение `mcp-server-odoo`.
- Альтернатива: server action / метод-обёртка `action_validate_from_api` с проверками прав и блокировкой инвентаризации.
- Запретить/не документировать обход через **`update_record({ state: 'done' })`** для pickings.

#### 2. Связка OR → PO → склад объекта

- Зафиксировать правило: PO из OR наследует **склад объекта** (`picking_type_id` = «ОбМ-N: Поступления»), `origin` = номер OR, `partner_ref` = номер счёта (1С).
- Проверить/доработать кастомный модуль **`object.request`**: кнопка «Создать заказ поставщику» с правильным складом; статусы строк (`qty_to_buy`, `qty_to_issue`).
- Связь **internal transfer** с OR (`origin` или поле `request_id`, если есть в модуле).

#### 3. Контроль номенклатуры для прихода

- При создании PO/picking через API проверять **`is_storable`** на товарах; иначе — ошибка агенту до Validate.
- Согласовать с **TD-002** (метры, не кг в строке прихода).

#### 4. Документация и права

- Обновить allowlist MCP (TD-001): `object.request*`, `purchase.order`, `stock.picking` — только нужные операции.
- Инструкция для снабженца: гибрид «API готовит → UI Validate» до полного API.

### Критерии готовности (Definition of Done)

- [ ] MCP (или RPC) вызывает **`button_confirm`** и **`button_validate`**; тест: PO → receipt → **quants** на ОбМ-4 без инвентаризации.
- [ ] PO из OR автоматически (или по чеклисту API) получает **верный** `picking_type_id` склада объекта.
- [ ] End-to-end тест: OR → PO (УТ-1132) → Validate → 1098 м на **ОбМ-4/Наличие** (или актуальные количества).
- [ ] [`instruction-warehouse-supply-cycle.md`](instruction-warehouse-supply-cycle.md) обновлена: раздел API помечен «реализовано».
- [ ] Нет регрессии: инвентаризация не используется в сценариях закупки.

### Ссылки

- Инструкция процесса: [`docs/instruction-warehouse-supply-cycle.md`](instruction-warehouse-supply-cycle.md).
- Кейс-референс: PO **P00010**, приход **ОбМ-4/IN/00001** (отменён), счёт **УТ-1132**.
- Модели: `object.request`, `purchase.order`, `stock.picking`, `stock.warehouse` (ОбМ-4, id 16).

## TD-004: Явная регистрация action tools вместо side-effect import

- **Статус**: открыто
- **Контекст**: в AI Assistant v3 read tools регистрируются в `default_registry` при импорте `services.action_tools.read_tools`. Для снижения риска пустого registry добавлен импорт `action_tools` из `custom_addons/ai_assistant/services/__init__.py`, но это остаётся side-effect регистрацией на уровне импорта.
- **Цель**: заменить неявную регистрацию на явную функцию `register_default_tools()` с идемпотентной защитой, чтобы повторный импорт/инициализация не создавали дублей и поведение загрузки было очевидным.

### Подзадачи

1. Добавить в `services/action_tools/registry.py` или отдельный модуль функцию `register_default_tools(registry=None)`.
2. Сделать регистрацию идемпотентной: повторный вызов не должен падать на уже зарегистрированных стандартных tools.
3. Убрать регистрацию из нижней части `read_tools.py` или оставить только через явную функцию.
4. Добавить тест: двойной вызов `register_default_tools()` не создаёт дублей и не выбрасывает ошибку.

### Критерии готовности (Definition of Done)

- [ ] Стандартные tools регистрируются явным вызовом при инициализации модуля.
- [ ] Повторная регистрация безопасна.
- [ ] Тест покрывает пустой registry, повторную регистрацию и наличие ключевых read tools.
