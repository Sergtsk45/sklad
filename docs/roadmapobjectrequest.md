## Цель

Подготовить roadmap для кастомного модуля Odoo 19, который закрывает процесс:

1. Прораб создает **требование на комплектацию объекта** на основании Excel-файла.
2. Снабженец проверяет потребность, решает, что выдать со склада, а что отправить в закупку.
3. Кладовщик подтверждает фактическую выдачу.
4. На дефицит формируются черновики закупки для дальнейшей ручной доработки.

Модуль должен опираться на стандартные механики Odoo, а не дублировать их:

- внутренний справочник товаров;
- `vendor info` / vendor pricelist;
- складские движения;
- резервирование;
- закупки и RFQ.

## Бизнес-контекст и границы

### Входит в задачу

- один основной документ: `Требование на комплектацию объекта`;
- один документ всегда относится к одному объекту;
- один объект может иметь много документов;
- в строках документа могут быть разные зоны/этажи/участки объекта;
- Excel используется только как источник импорта;
- импортируемая строка может требовать ручного сопоставления;
- выдача оформляется складским документом, близким к расходной накладной;
- в документе должны быть печатные формы.

### Не входит в MVP

- автоматический расчет наличия по складу;
- автоматическое создание RFQ;
- полноценное согласование;
- отчеты и дашборды;
- сценарий нескольких КП по одной позиции;
- финансовая логика по ценам и бюджетам;
- продвинутый экран сопоставления номенклатуры.

## Подтвержденные бизнес-правила

### Документ

- название: `Требование на комплектацию объекта`;
- один документ = один объект;
- объект трактуется как **стройка/проект**;
- документ содержит шапку и строки;
- в строках можно указывать зону, этаж, участок.

### Роли

- **Прораб**
  - создает документ;
  - может редактировать документ;
  - является инициатором потребности.
- **Снабженец**
  - может редактировать документ;
  - принимает решение, что выдать, а что закупать;
  - подготавливает закупку по дефициту.
- **Кладовщик**
  - может редактировать документ в рамках складской обработки;
  - подтверждает фактическую выдачу.
- **Согласующий**
  - роль предусмотрена, но в MVP только как заглушка.

### Excel

Формат Excel фиксированный. Колонки:

- номер п/п
- артикул поставщика (может быть `none`)
- наименование
- единица измерения
- количество
- цена
- комментарий
- поставщик

Правила импорта:

- прораб формирует Excel по внутренней номенклатуре;
- если строка не сопоставилась с товаром Odoo, она все равно импортируется;
- такая строка получает признак `требует сопоставления`;
- отдельный экран сопоставления в MVP считается заглушкой.

### Номенклатура

- в системе один внутренний справочник товаров;
- поставщики и их артикула хранятся через `vendor info`;
- у одного товара может быть несколько поставщиков;
- поставщик для закупки дефицита выбирается вручную снабженцем;
- логика “последний поставщик” может быть добавлена позже;
- в строке требования нужно хранить допустимые замены.

### Склад и выдача

- при расчете наличия учитывается только физический остаток;
- при частичном наличии строка должна автоматически делиться на:
  - `к выдаче`
  - `к закупке`
- выдача должна оформляться как расходная накладная;
- фактическую выдачу подтверждает кладовщик;
- нужна печатная форма на выдачу;
- резервирование под требование до фактической выдачи требуется.

### Закупка

- на дефицит создается только **черновик закупки** для ручной доработки;
- строки должны группироваться по поставщику;
- если у строки нет поставщика, она помечается как требующая ручного выбора;
- сценарий нескольких КП от разных поставщиков в MVP не реализуется, только закладывается как заглушка.

### Статусы

Статусы документа:

- `Черновик`
- `В работе`
- `Закрыто`
- `Отменено`

Статусы строк:

- `Частично выдано`
- `Полностью обеспечено`

Примечание: для технической реализации имеет смысл хранить более детальное вычисляемое состояние строки, а бизнесу показывать только утвержденные статусы.

## Как это должно лечь на стандартный Odoo

Ниже - опорные точки, которые подтверждены через документацию Odoo, извлеченную через Context7:

- карточка товара и закупка у поставщиков в Odoo уже поддерживают vendor pricelist / vendor info;
- закупочные документы строятся через RFQ / Purchase Order;
- внутренние и складские перемещения в Odoo реализованы через transfer/picking;
- в складской отчетности Odoo различаются `On Hand`, `Reserved`, `Incoming`, `Outgoing`;
- резервирование и проверка доступности уже встроены в складскую логику.

Практический вывод для модуля:

- не нужно создавать свой отдельный справочник поставщиков в строках документа;
- не нужно реализовывать свою складскую проводку;
- документ требования должен быть “оркестратором” поверх стандартных сущностей Odoo.

## Рекомендуемая архитектурная идея

### Основной принцип

Новый модуль не заменяет `stock` и `purchase`, а дает пользователю один рабочий документ, из которого запускаются стандартные действия Odoo.

### Основные сущности

- кастомный документ `object.request`
- кастомная строка `object.request.line`
- связи со стандартными моделями:
  - `project.project` или кастомная модель объекта
  - `product.product` / `product.template`
  - `res.partner` (прораб, поставщик)
  - `stock.picking`
  - `purchase.order`

## Предлагаемая модель данных

## 1. Шапка документа

Модель условно: `object.request`

Поля:

- `name` - номер документа
- `project_id` - объект / стройка / проект
- `foreman_id` - прораб
- `need_date` - дата потребности
- `priority` - приоритет
- `comment` - комментарий
- `state` - статус документа
- `line_ids` - строки
- `issue_picking_ids` - связанные расходные документы
- `purchase_order_ids` - связанные закупки
- `matching_state` - агрегированный статус сопоставления строк
- `approval_state` - поле-заглушка под согласование
- `source_file_name` - имя Excel-файла
- `imported_at` - дата импорта

### Поля шапки для печатной формы

- номер документа
- объект
- прораб
- дата потребности
- приоритет
- комментарий

## 2. Строка документа

Модель условно: `object.request.line`

Поля исходного импорта:

- `request_id`
- `sequence` - номер п/п
- `supplier_article`
- `name_raw`
- `uom_raw`
- `qty_requested`
- `price_raw`
- `comment`
- `supplier_raw`

Поля бизнес-обработки:

- `product_id`
- `uom_id`
- `zone`
- `floor`
- `section`
- `preferred_vendor_id`
- `allowed_substitute_ids`
- `matching_required`
- `matching_note`
- `procurement_mode`
- `qty_to_issue`
- `qty_to_buy`
- `qty_issued`
- `line_state`

### Рекомендуемые технические поля строки

- `stock_qty_on_hand`
- `stock_check_date`
- `manual_vendor_required`
- `issue_reserved`
- `issue_picking_id`
- `purchase_order_id`

### Почему нужны технические поля

Они упрощают:

- повторный пересчет;
- печатные формы;
- объяснимость для пользователя;
- переход к этапу 2 без миграции структуры.

## Жизненный цикл документа

## 1. Создание

Прораб создает документ:

- либо вручную;
- либо через импорт Excel.

После импорта документ получает статус `Черновик`.

## 2. Проверка и сопоставление

Снабженец открывает документ и видит:

- какие строки сопоставились;
- какие строки требуют ручного сопоставления;
- какие строки требуют выбора поставщика;
- допустимые замены.

На этом этапе документ остается в `Черновик` или переводится в `В работе`.

## 3. Обработка снабженцем

Снабженец определяет:

- что выдать;
- что закупать;
- что требует уточнения.

В MVP это может быть выполнено вручную по строкам.  
На этапе 2 логика дополняется автоматическим расчетом по физическому остатку.

## 4. Выдача со склада

По выбранным строкам создается складской документ выдачи.

С точки зрения UX пользователь видит это как:

- кнопка `Создать выдачу`
- результат: расходная накладная
- далее кладовщик подтверждает фактическую выдачу

Строка может получить статус:

- `Частично выдано`
- `Полностью обеспечено`

## 5. Закупка дефицита

По строкам дефицита:

- формируются черновики закупки;
- строки группируются по поставщику;
- строки без выбранного поставщика остаются в документе как требующие ручного выбора.

В MVP закупка - это заглушка на уровне roadmap.  
На этапе 2 это становится рабочим сценарием.

## 6. Закрытие

Документ переводится в `Закрыто`, когда:

- все строки либо обеспечены;
- либо явно отменены / исключены из обработки.

Это условие стоит явно зафиксировать при проектировании логики реализации.

## Целевой пользовательский workflow

## Сценарий 1. Прораб создает требование через Excel

1. Прораб открывает раздел `Требования на комплектацию объекта`.
2. Нажимает `Импорт из Excel`.
3. Загружает файл фиксированного формата.
4. Система создает документ по выбранному объекту.
5. Строки, которые не сопоставились, получают признак `Требует сопоставления`.
6. Документ сохраняется в статусе `Черновик`.

## Сценарий 2. Снабженец подготавливает документ к исполнению

1. Открывает документ.
2. Проверяет шапку, строки и результат импорта.
3. Выполняет ручное сопоставление строк, если требуется.
4. Проверяет и при необходимости задает поставщика.
5. Указывает допустимые замены.
6. Переводит документ в `В работе`.

## Сценарий 3. Выдача части со склада

1. Снабженец определяет строки и количества к выдаче.
2. Создается документ выдачи.
3. Резервируются товары под требование.
4. Кладовщик подтверждает фактическую выдачу.
5. В строках фиксируются выданные количества.

## Сценарий 4. Передача дефицита в закупку

1. Снабженец выбирает строки к закупке.
2. Система группирует строки по поставщику.
3. Формируются черновики закупки.
4. Снабженец вручную дорабатывает закупки в стандартном интерфейсе Odoo.

## MVP

В MVP включить только то, что прямо требуется для первого рабочего контура.

### Входит в MVP

- каталог документов `Требование на комплектацию объекта`
- шапка документа:
  - объект
  - прораб
  - дата потребности
  - приоритет
  - комментарий
- строки документа
- импорт Excel фиксированного формата
- создание строк со статусом `требует сопоставления`
- ручное сопоставление строк
- привязка к объекту
- ручное управление частичной выдачей
- печатная форма требования
- печатная форма выдачи
- заглушка под согласование

### Не входит в MVP

- использование цены в бизнес-логике
- автоматический расчет физического остатка
- автоматический split на `к выдаче/к закупке`
- автоматическое создание RFQ
- отчеты
- дашборд
- многопоставочный тендер/несколько КП

## Этап 2

На втором этапе добавить автоматизацию.

### Входит в этап 2

- расчет наличия по физическому остатку;
- автоматическое заполнение:
  - `к выдаче`
  - `к закупке`
- создание черновиков RFQ / Purchase;
- группировка по поставщику;
- резервирование под требование;
- согласование;
- отчеты.

## Предлагаемая реализация по этапам

- прорабы;
- товары;
- поставщики;
- vendor info.

### Почему это критично

## Odoo-механики, на которые стоит опереться

### Товары и поставщики

Для закупки и выбора поставщика использовать стандартную логику Odoo:

- товар должен быть нормализован во внутреннем справочнике;
- поставщики и условия поставки хранятся в карточке товара;
- при необходимости later stage можно использовать “последнего поставщика”.

### Склад

Для выдачи использовать стандартные складские документы Odoo:

- движения;
- резервирование;
- подтверждение выполнения;
- печатные формы на базе stock picking report.

### Закупка

Для дефицита использовать стандартный purchase flow:

- черновик RFQ / закупки;
- ручная доработка снабженцем;
- подтверждение уже в стандартном purchase интерфейсе.

## Риски

### 1. Отсутствие справочников

Сейчас у проекта нет мастер-данных:

- товары
- объекты
- поставщики

Это означает, что MVP модуля нужно проектировать так, чтобы он терпимо жил в режиме неполного справочника.

### 2. Импорт может быть “грязным”

Даже если Excel формально одного формата, реальные файлы могут содержать:

- пустые артикулы;
- неединообразные единицы измерения;
- разные написания поставщиков;
- лишние пробелы и комментарии.

### 3. Разрыв между бизнес-термином и термином Odoo

Пользователь говорит “расходная накладная”, а Odoo может хранить это как `stock.picking` / transfer.  
Это нужно учесть в UX и печатных формах.

### 4. Закрытие документа требует четкого правила

Нужно заранее зафиксировать:

- можно ли закрывать документ с несопоставленными строками;
- можно ли закрывать документ с отмененными строками;
- обязателен ли полный выпуск или закупка по каждой строке.

## Open questions

Хотя требований уже достаточно для roadmap, при проектировании модуля стоит дополнительно уточнить:

- использовать `project.project` как объект или вводить отдельную модель объекта;
- где именно хранить зоны/этажи/участки:
  - отдельными полями
  - единым текстовым полем
  - отдельной связанной сущностью;
- закрытие документа:
  - только после полного обеспечения
  - или после явного решения пользователя;
- должна ли цена из Excel сохраняться только “для справки” уже в MVP.

## Критерии готовности MVP

- пользователь может создать документ по объекту;
- можно импортировать Excel фиксированного формата;
- строки сохраняются даже при несопоставленной номенклатуре;
- снабженец может вручную сопоставить строки;
- можно указать поставщика и допустимые замены;
- можно частично выдать материалы со склада;
- кладовщик может подтвердить фактическую выдачу;
- доступны печатные формы требования и выдачи;
- документ проходит путь `Черновик -> В работе -> Закрыто`.

## Рекомендация по следующему шагу

После roadmap логично делать не сразу код, а сначала **functional spec** и **data model spec**:

1. уточнить выбор модели объекта;
2. зафиксировать точные поля шапки и строки;
3. описать UI-экраны;
4. описать wizard импорта Excel;
5. отдельно описать сценарий выдачи и печатную форму.

Такой порядок снизит риск перед реализацией кастомного модуля.
