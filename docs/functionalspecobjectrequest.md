## Цель документа

Описать функциональные требования к экранным формам, кнопкам и пользовательскому поведению для кастомного Odoo 19 модуля `Требование на комплектацию объекта`.

Этот документ не описывает внутреннюю реализацию моделей и методов на уровне кода. Его задача:

- зафиксировать состав экранов;
- определить, что именно видит пользователь;
- определить, какие кнопки доступны в каждом состоянии;
- зафиксировать права ролей на уровне UI;
- дать основу для последующей реализации views, wizards и печатных форм.

Документ опирается на `docs/roadmapobjectrequest.md`.

## Область действия

Functional spec покрывает:

- список документов требований;
- форму документа;
- строки документа;
- wizard импорта Excel;
- базовую ручную обработку строк;
- создание документа выдачи;
- печатные формы требования и выдачи;
- UI-заглушки под этап 2.

## Роли и ожидания от интерфейса

### Прораб

Основной сценарий:

- создать требование;
- заполнить шапку;
- импортировать Excel;
- просмотреть строки;
- передать документ в работу.

Что важно в UI:

- минимум лишних полей;
- понятный импорт;
- явный индикатор проблемных строк;
- печатная форма требования.
- отсутствие выбора склада при создании требования.

### Снабженец

Основной сценарий:

- открыть документ;
- проверить импорт;
- сопоставить строки;
- указать поставщика и замены;
- определить, что идет на выдачу, а что в закупку;
- проверить остатки по всем активным складам;
- вручную поправить распределение выдачи по складам;
- массово отправить строки в закупку или выдачу;
- сформировать связанные документы.

Что важно в UI:

- быстрый доступ к строкам с ошибками;
- массовые действия;
- визуально понятные количества;
- статус по каждой строке.

### Кладовщик

Основной сценарий:

- открыть связанную выдачу;
- подтвердить фактическую выдачу;
- распечатать расходную накладную.

Что важно в UI:

- только нужные поля;
- понятная форма выдачи;
- защита от лишнего редактирования.

### Согласующий

В MVP:

- отдельная логика согласования не реализуется;
- в UI должна быть предусмотрена заглушка под будущий этап.

## 2.1 Header

В header должны находиться кнопки, доступные в зависимости от состояния и роли.

### Кнопки header

- `Сохранить`
- `Отменить`
- `Импорт из Excel`
- `Перевести в работу`
- `Создать выдачу`
- `Рассчитать наличие`
- `Авто-разбивка`
- `Подготовить закупку`
- `Распечатать требование`
- `Закрыть`
- `Отменить документ`

### Правила видимости header-кнопок

#### `Импорт из Excel`

Доступна:

- в статусе `Черновик`
- для ролей: Прораб, Снабженец

Скрыта:

- в `Закрыто`
- в `Отменено`

#### `Перевести в работу`

Доступна:

- из `Черновик`
- для Прораба и Снабженца

Бизнес-правило:

- можно нажать, даже если в документе есть строки `требует сопоставления`, если так решит бизнес;
- но желательно показать предупреждение.

#### `Создать выдачу`

Доступна:

- в `В работе`
- для Снабженца

Условие:

- есть хотя бы одна строка с количеством к выдаче.

Кнопка открывает wizard предпросмотра, где строки сгруппированы по складам. Один склад равен одной будущей выдаче.

#### `Подготовить закупку`

Доступна:

- в `В работе`
- для Снабженца

Условие:

- есть хотя бы одна строка, требующая закупки или ручного выбора поставщика.

Создаёт draft `purchase.order`; приёмка идёт на склад объекта.

#### `Рассчитать наличие`

Доступна:

- в `В работе`
- для Снабженца

Поведение:

- система проверяет все активные склады компании;
- по каждой строке создаёт или обновляет распределение `object.request.line.stock`;
- если есть остатки, открывает предупреждение `Есть на складе`;
- если остатков нет, показывает notification.

#### `Авто-разбивка`

Доступна:

- после расчёта наличия;
- для Снабженца.

Поведение:

- планирует выдачу по складам;
- остаток отправляет в закупку;
- если снабженец вручную менял план, перед перезаписью показывает подтверждающий wizard.

#### `Распечатать требование`

Доступна:

- всегда, кроме `Отменено` при желании
- для всех ролей с доступом к документу

#### `Закрыть`

Доступна:

- в `В работе`
- для Снабженца

#### `Отменить документ`

Доступна:

- в `Черновик`
- в `В работе`
- только для Снабженца или администратора

## 2.2 Статусбар

Статусбар документа:

- `Черновик`
- `В работе`
- `Закрыто`
- `Отменено`

Цветовая индикация:

- Черновик: серый
- В работе: синий/фиолетовый
- Закрыто: зеленый
- Отменено: красный

## 2.3 Шапка документа

### Поля шапки

- `Номер`
- `Объект`
- `Прораб`
- `Дата потребности`
- `Приоритет`
- `Комментарий`
- `Источник импорта`
- `Дата импорта`
- `Статус сопоставления`
- `Согласование` (заглушка)

Поля `Склад` в шапке нет. Склад приёмки определяется объектом, а склад выдачи определяется строками распределения.

### Правила редактирования

#### В `Черновик`

Редактируются:

- объект
- прораб
- дата потребности
- приоритет
- комментарий

#### В `В работе`

Редактирование ограничивается:

- комментарий
- отдельные поля по решению бизнеса

Объект и прораб лучше замораживать.

#### В `Закрыто` и `Отменено`

Форма только для чтения.

## Экран 3. Таблица строк документа

Это ключевой UI-элемент.

### Колонки строк

Нужно показать пользователю одновременно импортированные и рабочие данные.

Рекомендуемый набор колонок:

- №
- зона
- этаж
- участок/секция
- артикул поставщика
- исходное наименование
- товар Odoo
- ед. изм.
- количество запрошено
- поставщик
- допустимые замены
- количество к выдаче
- количество к закупке
- общий остаток по складам
- зарезервировано
- выдано
- статус строки
- комментарий

### Визуальные индикаторы

Для строк нужны badges/иконки:

- `Требует сопоставления`
- `Требует поставщика`
- `Есть замены`
- `Частично выдано`
- `Полностью обеспечено`

### Inline actions в строке

Желательные кнопки/иконки:

- `Сопоставить`
- `Очистить сопоставление`
- `Выбрать поставщика`
- `Указать замены`
- `Открыть товар`

### Редактируемость строк

#### По статусу документа

В статусе `Черновик` можно добавлять и удалять строки и менять запрошенное
количество (`qty_requested`).

В статусе `В работе` состав строк фиксируется:

- нельзя добавить строку;
- нельзя удалить строку;
- нельзя изменить `qty_requested`.

Снабженец по-прежнему может сопоставлять товар, выбирать поставщика и менять
план выдачи/закупки (`qty_to_issue`, `qty_to_buy`, распределение по складам).

В статусах `Закрыто` и `Отменено` строки полностью readonly.

#### Прораб

Может редактировать:

- комментарий строки
- зона/этаж/участок

Не должен менять:

- складскую обработку
- закупочную обработку
- распределение по складам

#### Снабженец

Может редактировать:

- товар
- поставщика
- замены
- количества к выдаче/к закупке
- распределение `к выдаче` по складам
- состояние обработки

Дополнительные действия снабженца:

- `Закупить всё` — обнуляет выдачу по складам и переносит остаток строки в закупку;
- `Выдать максимум` — повторяет авто-разбивку по доступному остатку;
- `Сбросить разбивку` — очищает план выдачи и закупки;
- ручная правка `К выдаче со склада` в распределении ставит флаг ручного изменения плана.

#### Кладовщик

Может видеть:

- строки, попавшие в выдачу

Может редактировать:

- только фактическое выданное количество через связанную выдачу

## Экран 4. Wizard `Импорт из Excel`

### Назначение

Загрузить Excel в документ или создать документ на его основе.

### Поля wizard

- `Файл Excel`
- `Объект`
- `Прораб`
- `Дата потребности`
- `Приоритет`
- `Комментарий`

### Кнопки wizard

- `Загрузить и проверить`
- `Импортировать`
- `Отмена`

### Поведение

#### `Загрузить и проверить`

Система:

- проверяет, что файл читается;
- проверяет структуру колонок;
- показывает результат предварительной проверки.

#### `Импортировать`

Система:

- создает документ;
- создает строки;
- отмечает несопоставленные строки как проблемные.

### Сообщения пользователю

После проверки wizard должен показать:

- количество строк в файле
- количество успешно распознанных
- количество строк без сопоставления
- количество строк без поставщика
- список ошибок формата

### MVP поведение при ошибках

- если формат сломан критически — импорт запрещается;
- если часть строк не сопоставилась — импорт разрешается, но документ получает предупреждение.

## Экран 5. Ручное сопоставление строк

В MVP отдельный экран допускается как заглушка. Поэтому минимально достаточно встроенного режима внутри формы документа.

### Минимальный сценарий

Снабженец в таблице строк:

- выбирает товар Odoo;
- выбирает поставщика;
- указывает допустимые замены;
- снимает флаг `требует сопоставления`.

### Что должно ускорять работу

- фильтр `Только проблемные строки`
- массовое действие `Назначить поставщика`
- быстрый поиск товара по имени/артикулу

### Кнопки блока сопоставления

- `Сопоставить товар`
- `Назначить поставщика`
- `Сохранить`

## Экран 6. Действие `Создать выдачу`

### Назначение

На основании документа требования подготовить складской документ выдачи.

### Актуальный multi-warehouse сценарий

Пользовательский сценарий:

1. Снабженец нажимает `Создать выдачу`
2. Система открывает wizard `Предпросмотр выдач`
3. Wizard показывает группы по складам
4. Снабженец проверяет источник, назначение, дату, комментарий и флаг `Создать`
5. Система создаёт по одному `stock.picking` на каждую включённую группу
6. Открывается список созданных выдач

### Группа wizard

Для каждой группы показывается:

- склад;
- тип операции;
- локация-источник;
- локация-назначение;
- дата выдачи;
- комментарий;
- количество строк и суммарное количество;
- включена ли группа в создание.

### Если строк нет

Показывать понятную ошибку:

- `Нет строк с заполненным количеством к выдаче. Заполните распределение по складам.`

### После создания

На документе требования:

- появляется smart button `Выдачи`
- строки распределения получают связь с `stock.picking` и `stock.move`
- строка требования хранит агрегированное количество к выдаче и резерв

## Экран 6a. Распределение по складам

### Назначение

Показать снабженцу и кладовщику, сколько доступно и сколько планируется выдать с каждого склада.

### Доступность

- Прораб: не видит детальную таблицу распределения, только итоги по строке.
- Снабженец: видит и редактирует `К выдаче со склада`.
- Кладовщик: видит распределение только на чтение.

### Колонки

- склад;
- доступно;
- к выдаче;
- зарезервировано;
- дата проверки;
- созданная выдача.

### Авто-разбивка

Алгоритм:

- использует склад объекта первым, если на нём есть положительный остаток;
- не планирует выдачу со склада объекта при нулевом остатке;
- дальше минимизирует количество складов: если один склад закрывает потребность, выбирает его; иначе берёт склады по убыванию доступного остатка;
- не превышает `qty_requested - qty_issued`;
- дефицит переносит в `К закупке`.

## Экран 7. Форма выдачи / расходной накладной

### Назначение

Кладовщик подтверждает фактическую выдачу.

### Источник

Фактически это должен быть стандартный Odoo-документ складского движения, но для пользователя нужно показывать бизнес-термин:

- `Расходная накладная`

### Что нужно видеть пользователю

- номер выдачи
- объект
- исходный документ требования
- список позиций
- количество к выдаче
- фактически выдано
- статус выдачи

### Кнопки

- `Подтвердить выдачу`
- `Распечатать`
- `Вернуться к требованию`

### Кто может нажимать

- Кладовщик
- Снабженец

Но финальное подтверждение выдачи должно быть за кладовщиком.

## Печатная форма 2. Расходная накладная

### Назначение

Фиксация выдачи на объект.

### Содержимое

Шапка:

- номер документа выдачи
- ссылка на требование
- объект
- дата

Таблица:

- №
- товар
- ед. изм.
- количество
- зона/этаж/участок

Подписи:

- кладовщик
- получатель / представитель объекта

## Правила доступности кнопок по статусам

### Статус `Черновик`

Доступно:

- редактирование шапки
- импорт Excel
- ручное редактирование строк
- печать требования
- перевод в работу
- отмена документа

Недоступно:

- закрытие
- создание выдачи
- закупка

### Статус `В работе`

Доступно:

- ограниченное редактирование
- ручное сопоставление
- создание выдачи
- подготовка закупки
- печать требования
- закрытие
- отмена

### Статус `Закрыто`

Доступно:

- только просмотр
- печать
- просмотр связанных документов

### Статус `Отменено`

Доступно:

- только просмотр

## Правила доступности по ролям

### Прораб

Доступно:

- создать документ
- редактировать шапку и часть строк
- импортировать Excel
- печатать требование

Недоступно:

- подтверждать выдачу
- формировать закупку

### Снабженец

Доступно:

- полная рабочая обработка документа
- сопоставление строк
- указание поставщика
- указание замен
- создание выдачи
- подготовка закупки
- закрытие документа

### Кладовщик

Доступно:

- просмотр документа
- просмотр строк к выдаче
- подтверждение фактической выдачи
- печать расходной накладной

### Согласующий

В MVP:

- UI-заглушка
- без полноценного action-flow

## UI-заглушки этапа 2

В интерфейсе уже сейчас можно предусмотреть элементы, которые пока не работают полностью:

- поле `Физический остаток`
- поле `К закупке` в auto mode
- кнопка `Рассчитать наличие`
- кнопка `Подготовить закупку`
- поле `Согласование`

### Требование к UX

Если кнопка является заглушкой, пользователь должен это понимать.  
Лучше показать:

- disabled button
- tooltip `Будет доступно на этапе 2`

## Основные сценарии тестирования UI

### Сценарий 1

- Прораб создает документ вручную
- Заполняет шапку
- Сохраняет

### Сценарий 2

- Прораб импортирует Excel
- Часть строк не сопоставляется
- Документ создается
- Проблемные строки видны в таблице

### Сценарий 3

- Снабженец открывает проблемные строки
- Назначает товар и поставщика
- Документ переводится в `В работе`

### Сценарий 4

- Снабженец формирует выдачу
- Кладовщик открывает выдачу
- Подтверждает фактическое количество

### Сценарий 5

- Пользователь печатает требование
- Пользователь печатает расходную накладную

## Критерии готовности functional spec

- определены все основные пользовательские экраны;
- определены поля на форме документа;
- определены кнопки и их видимость;
- определены права ролей на уровне UI;
- определены печатные формы;
- определены базовые заглушки для этапа 2;
- документ можно использовать как базу для проектирования Odoo views и wizards.
