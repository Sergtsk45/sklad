# Task Tracker: Событие в календаре при оплате счёта поставщика (Bill → calendar.event)

**Дата создания:** 2026-08-08
**Обновлено:** 2026-08-08 (два раунда ревью: механизм триггера/занятость/приглашения/таймзона — всё подтверждено чтением исходников Odoo)
**Инстанс:** Odoo 19 **Community**
**Статус:** ✅ Задеплоена на prod 2026-08-08 (`d429771`, `object_request_calendar` 19.0.1.0.0 installed)
**Краткое описание:** при переходе счёта поставщика (vendor bill) в статус «Оплачен» в календаре автоматически создаётся встреча (`calendar.event`) длительностью 1 час в первом свободном рабочем слоте на дату потребности (`object.request.need_date`) связанного требования; далее пользователь свободно двигает/растягивает встречу в стандартном UI приложения «Календарь».

---

## Зафиксированные решения (входные ограничения для агента)

Эти решения даны пользователем в диалоге, агент не должен заменять их альтернативами без отдельного согласования:

1. **Триггер (бизнес-событие):** `account.move` с `move_type = 'in_invoice'` (vendor bill), переход `payment_state → 'paid'`. Customer invoices (`out_invoice`) не участвуют. *(Технический способ детектирования перехода — см. раздел «Исправленный механизм триггера» ниже, скорректирован после ревью.)*
2. **Источник даты:** только `object.request.need_date`. Fallback на дату счёта/сегодня — не использовать.
3. **Целевой объект в календаре:** именно **встреча** `calendar.event` (не `project.task` — в Community у задач нет полноценных start/stop для drag/resize).
4. **Участники по умолчанию:** снабженец (`object.request.buyer_user_id`) и прораб (`object.request.foreman_user_id`) связанного требования. `foreman_user_id` в модели `object.request` **обязательное поле** — сценарий «оба участника пусты» невозможен, может быть пуст только `buyer_user_id`.
5. **Длительность:** фиксированная **1 час** на момент создания; дальнейшее изменение даты/длительности — вручную, штатным drag-and-drop календаря Odoo.
6. **Редакция:** Community — не использовать Enterprise-only поля/модули (`planned_date_begin`, Gantt, `project_forecast`, `planning`).
7. **Рабочее время и поиск слота:** событие ставится в **первый свободный часовой слот** рабочего дня `09:00–16:00` (обед `12:00–13:00` исключён). Занятость проверяется **только по календарю снабженца** (`buyer_user_id`). Если весь день занят — поиск продолжается на **следующий рабочий день** (пропуская сб/вс).
8. **Часовой пояс (решено 2026-08-08, скорректировано после ревью):** всегда **часовой пояс компании**. ⚠️ Технически поля `tz` на `res.company` **не существует** (проверено в `odoo/odoo/addons/base/models/res_company.py`) — часовой пояс есть только на `res.partner` (`res_partner.py:223`). Источник: **`move.company_id.partner_id.tz`**, с явным **fallback на `'UTC'`**, если поле не заполнено (чтобы реализация не падала и не «плавала» по TZ текущего пользователя). Без привязки к TZ снабженца или пользователя, проводящего оплату.
9. **Горизонт поиска слота (решено 2026-08-08):** **30 календарных дней** от `need_date`. Если за это время свободный слот не найден — событие **всё равно создаётся** в первом слоте (`09:00–10:00`) первого рабочего дня после горизонта, **даже если он конфликтует** с другим событием снабженца (наложение допустимо как осознанный fallback).
10. **Что считается «занято» (решено 2026-08-08):** блокирует слот только активное событие снабженца с `show_as = 'busy'` (**`show_as = 'free'` слот НЕ блокирует**).
11. **Приглашения (решено 2026-08-08, скорректировано после ревью):** встреча создаётся **без email-рассылки** снабженцу/прорабу — но **только в момент автоматического создания**. Технически: `self.env['calendar.event'].with_context(no_mail_to_attendees=True).create(vals)` (контекстный ключ подтверждён в `calendar_attendee.py:140` — гасит именно `_notify_attendees`, не меняет поведение события навсегда). Если пользователь позже вручную подвинет/переименует встречу — штатные уведомления календаря Odoo продолжат работать как обычно (это осознанное отличие от изначально предложенного `override _skip_send_mail_status_update()`, который отключил бы уведомления на весь жизненный цикл встречи).
12. **need_date на выходном без снабженца (решено 2026-08-08, подтверждено повторно despite рекомендации ревью):** если `buyer_user_id` пуст, событие ставится **ровно на `need_date`** в `09:00–10:00`, **даже если это суббота/воскресенье** — без переноса на ближайший будний день.
13. **Название встречи (добавлено после ревью 2026-08-08):** `calendar.event.name` обязательное поле, шаблон: `"Оплата {bill.name} — {object_request.name}"`, например `"Оплата BILL/2026/08/0002 — OR/2026/08/0032"`. В `description` — краткий текст с суммой bill и ссылкой на требование.
14. **Повторная проверка перед фактическим созданием (добавлено после ревью 2026-08-08):** precommit-колбэк обязан **заново прочитать `payment_state`** у bill непосредственно перед созданием события (не полагаться на факт постановки в очередь). Если к моменту выполнения колбэка `payment_state` уже **не `'paid'`** (сценарий `paid → not_paid` в рамках той же транзакции, например отмена платежа) — событие **не создаётся**.

## ⚠️ Исправленный механизм триггера (после технического ревью 2026-08-08)

**Проблема с первоначальным планом:** `docs/tasktracker-invoice-paid-calendar-event.md` предлагал override `account.move.write()` для детекта перехода `payment_state → 'paid'`. Это **ненадёжно**, что подтверждено в исходниках Odoo:

```600:603:odoo/addons/account/models/account_move.py
    payment_state = fields.Selection(
        ...
        compute='_compute_payment_state', store=True, readonly=True,
```

`payment_state` — **вычисляемое (`compute`) хранимое поле**. При регистрации оплаты ORM пересчитывает его через `_compute_payment_state()` после изменения сверок/строк проводки — **не обязательно вызывая `write()` на `account.move` с новым значением поля напрямую**. Override `write()` может просто не сработать в реальном сценарии оплаты через мастер «Зарегистрировать платёж» / «Оплатить», хотя сработает на синтетическом `bill.write({'payment_state': 'paid'})` в тесте — что создаёт ложное чувство надёжности.

**Исправленное решение:**

1. Override **`_compute_payment_state()`** на `account.move` (а не `write()`):
   - перед вызовом `super()._compute_payment_state()` — снять снимок текущих (старых) значений `payment_state` для `self`;
   - вызвать `super()._compute_payment_state()`;
   - сравнить старое и новое значение для каждой записи; для тех, где переход именно `!= 'paid' → 'paid'` и `move_type == 'in_invoice'` — запланировать создание события.
2. Создание события **не выполнять синхронно внутри compute** (это небезопасно — compute может вызываться многократно в рамках пересчёта зависимостей в одной транзакции). Вместо этого — поставить в очередь через `self.env.cr.precommit.add(...)`, с дедупликацией по `move.id` (например, множество id в `self.env.cr.precommit.data`), чтобы создание реально произошло **один раз** после того, как все пересчёты в транзакции завершились и значения стабилизировались.
3. **Обязательное условие приёмки:** проверять переход **интеграционным тестом через реальный мастер оплаты** (`account.payment.register` / кнопка «Зарегистрировать платёж», как в живой проверке 2026-08-08 на `BILL/2026/08/0002`), а не только через прямой `bill.write({'payment_state': 'paid'})`. Прямой `write()` полезен как дополнительный, но не основной тест.

## Правило определения «занятости» слота (детализировано после ревью)

Помимо `show_as = 'busy'` (см. решение №10), приняты следующие технические умолчания агента (не требуют отдельного подтверждения пользователя, но подлежат пересмотру при обнаружении проблем в тестах):

- Архивные события (`active = False`) слот **не блокируют** (стандартный `search()` их и так не возвращает без `active_test=False`).
- **All-day** событие блокирует **весь рабочий день** снабженца (все 6 слотов), а не конкретный час.
- Если снабженец — **организатор** события (`user_id`), оно блокирует слот **независимо** от статуса участников.
- Если снабженец — обычный **участник** (`partner_ids`/`attendee_ids`) и его статус `declined` — событие слот **не блокирует**; для остальных статусов (`needsAction`, `tentative`, `accepted`) — блокирует.
- Пересечение по времени — точное (`event.start < slot_stop and event.stop > slot_start`), без выравнивания на границу часа.

## Правило рабочего времени и поиска свободного слота (алгоритм)

1. Рабочие часовые слоты дня (будни, пн–пт): `09:00–10:00`, `10:00–11:00`, `11:00–12:00`, `13:00–14:00`, `14:00–15:00`, `15:00–16:00` (обед `12:00–13:00` — не слот). Итого 6 слотов/день, время — по часовому поясу компании.
2. Начиная с `need_date`, для каждого рабочего дня (пропуская сб/вс) перебираем слоты **по порядку** и берём **первый**, который не пересекается по времени ни с одним `calendar.event` снабженца, блокирующим слот (см. правило занятости выше).
3. Если весь день без свободных слотов — переходим на следующий рабочий день и повторяем шаг 2.
4. **Горизонт 30 календарных дней** от `need_date`: если свободный слот не найден — принудительно создать событие в `09:00–10:00` первого рабочего дня после горизонта (наложение допустимо), с пометкой в chatter, что слот подобран «через силу».
5. **Edge-case «снабженец не назначен»:** если `buyer_user_id` пуст — слот `09:00–10:00` **строго на `need_date`** без поиска и без переноса на будний день, даже если `need_date` — выходной.

## Архитектурное решение

- Новый лёгкий модуль **`object_request_calendar`** (не нагружаем `object_request` учётной/календарной логикой). Зависимости: `object_request`, `calendar`, `account`, `purchase`.
- **Резолвер цепочки:** `account.move` (bill) → `account.move.line.purchase_line_id.order_id` (→ `purchase.order`) → `object.request` (поиск по `purchase_order_ids in po_ids`). Поиск — через `sudo()` с явным ограничением по `company_id`, так как пользователь бухгалтерии, проводящий оплату, может не иметь прав на `object.request` (обычный `search()` в этом случае тихо вернёт неполный/пустой результат).
- **Поля трассировки на `calendar.event`:** `object_request_id` (`Many2one`, `ondelete='set null'`), `source_bill_id` (`Many2one`, `ondelete='set null'`) — для идемпотентности и для смарт-кнопки. На `object.request` — обычный `fields.One2many('calendar.event', 'object_request_id')` (не «computed через search», так как обратное поле физически существует).
- **Идемпотентность:** SQL-уникальность пары `(object_request_id, source_bill_id)`. Перед повторным поиском и созданием берётся транзакционная PostgreSQL advisory-блокировка пары bill/request; это сериализует конкурирующие обработчики без вложенного flush/rollback внутри precommit. SQL UNIQUE остаётся последней защитой.
- **Поиск слота:** сервисный метод поиска первого свободного часового слота по правилу выше.
- **Хук создания:** override `_compute_payment_state()` + отложенное выполнение через `precommit` (см. раздел «Исправленный механизм триггера»), с повторной проверкой `payment_state == 'paid'` непосредственно перед созданием (решение №14).
- **Видимость:** на форме `object.request` — `calendar_event_ids` (One2many) + счётчик + смарт-кнопка «Встречи» рядом с «Закупки»/«Выдачи».
- **Часовой пояс:** `move.company_id.partner_id.tz or 'UTC'` (решение №8; на `res.company` поля `tz` не существует).
- **Отключение email-приглашений:** `self.env['calendar.event'].with_context(no_mail_to_attendees=True).create(vals)` — гасит рассылку только для этого создания, не меняет поведение события при последующих ручных изменениях (решение №11).
- **Название события:** шаблон `"Оплата {bill.name} — {object_request.name}"` (решение №13).
- **Новых моделей нет** → `security/ir.model.access.csv` для новой модели не требуется (только если появятся новые поля с ограничениями доступа — маловероятно).
- **Chatter:** сообщение о созданной встрече публикуется **в обоих документах** (`object.request` и `account.move`) при успешном создании; **только в `account.move`** — если по bill не найдено ни одного `object.request` (нечего дополнять).

## Риски

- Дубликаты событий при многократном пересчёте `payment_state` в рамках одной транзакции — закрыто дедупликацией precommit (ICE-005) + SQL-констрейнтом (ICE-003).
- m2m `object.request.purchase_order_ids` не гарантирует 1:1 с bill — возможны кейсы «несколько OR на одну закупку», см. тесты ICE-004.
- Организационный вопрос охвата: часть bill может по-прежнему проводиться через 1С, а не Odoo — для таких bill автоматизация не сработает (ожидаемое поведение, не баг), см. раздел «Открытые вопросы».
- Производственный календарь/праздники (кроме сб/вс) не учитываются в MVP.
- Override `_compute_payment_state()` — более инвазивный способ, чем `write()`; при обновлении ядра Odoo (минорные версии 19.x) сигнатура/логика compute-метода может измениться — при апгрейде ядра проверять регрессионным тестом ICE-007.
