## 2. Список разделов roadmap

### 2.1. Цель
- Один документ = один объект.
- Один объект может иметь много документов.
- В документе есть строки по разным зонам, этажам, участкам.

### 2.2. Основные правила
- Документ создаёт прораб.
- Редактирование доступно ролям: прораб, снабженец, кладовщик.
- Решение "выдача / закупка" принимает снабженец.
- Заполнение строк идёт по внутренней номенклатуре.
- Excel импортируется в одном фиксированном формате.
- Несопоставленные строки создаются и получают признак "требует сопоставления".
- Экран сопоставления в MVP допускается как простая заглушка с ручным выбором.
- Наличие считается только по физическому остатку.
- При частичном наличии строка автоматически делится на объём к выдаче и к закупке.
- Выдача оформляется через расходную накладную, но подтверждается кладовщиком.
- До фактической выдачи нужен резерв.
- Закупка создаётся только как черновик RFQ для ручной доработки.
- Группировка закупки выполняется по поставщику.
- Если поставщик не выбран, строка требует ручного выбора.
- Сценарий нескольких КП на этапе 1 не реализуется.
- В MVP цены не используются.
- Дашборд не нужен.

### 2.3. Пользовательские сценарии
- Прораб создаёт документ по объекту и импортирует Excel.
- Система создаёт строки и отмечает несопоставленные позиции.
- Снабженец вручную сопоставляет проблемные строки.
- Снабженец определяет по строке: выдача, закупка или смешанный сценарий.
- При частичном наличии система раскладывает объём на склад и закупку.
- Кладовщик подтверждает фактическую выдачу.
- Снабженец формирует черновик RFQ по закупаемым строкам.
- Пользователь печатает требование и печатную форму выдачи.

### 2.4. Интеграции
- `product.product` / `product.template`: внутренняя номенклатура.
- `product.supplierinfo`: vendor info и варианты поставщиков.
- `stock.quant`: физический остаток.
- `stock.picking`: расходная накладная и резерв.
- `purchase.order`: черновик RFQ.
- `ir.actions.report`: печатная форма требования и выдачи.

## 3. Рекомендуемая модель данных

### 3.1. Шапка документа
**Модель:** `object.supply.request`

**Основные поля:**
- `name` - номер документа.
- `project_object_id` - объект.
- `foreman_id` - прораб.
- `need_date` - дата потребности.
- `priority` - приоритет.
- `comment` - комментарий.
- `state` - статус документа: `draft`, `in_progress`, `closed`, `cancelled`.
- `line_ids` - строки документа.
- `company_id` - компания.
- `currency_id` - валюта, опционально на будущее.
- `import_file` / `import_filename` - исходный Excel для аудита импорта.
- `matching_state` - агрегатный статус сопоставления: `all_matched`, `partially_matched`, `need_matching`.
- `picking_ids` - связанные выдачи.
- `purchase_order_ids` - связанные RFQ.

### 3.2. Строка документа
**Модель:** `object.supply.request.line`

**Бизнес-поля:**
- `request_id` - ссылка на шапку.
- `sequence` - номер строки.
- `zone` - зона.
- `floor` - этаж.
- `section` - участок.
- `source_row_no` - номер строки из Excel.
- `supplier_article` - артикул поставщика, может быть пустым.
- `name_raw` - исходное наименование из Excel.
- `product_id` - внутренняя номенклатура.
- `uom_id` - единица измерения.
- `qty_requested` - требуемое количество.
- `comment` - комментарий строки.
- `supplier_id` - выбранный поставщик.
- `allowed_substitute_ids` - допустимые замены.

**Поля процесса:**
- `matching_required` - требует сопоставления.
- `matching_note` - комментарий по сопоставлению.
- `stock_qty_available` - физический остаток на момент расчёта.
- `qty_to_issue` - к выдаче со склада.
- `qty_to_buy` - к закупке.
- `qty_issued` - фактически выдано.
- `procurement_mode` - `issue`, `buy`, `mixed`, `manual`.
- `fulfillment_state` - рекомендовано хранить как вычисляемое поле:
  - `none` - ещё не обеспечено;
  - `partial` - частично выдано;
  - `full` - полностью обеспечено.

### 3.3. Справочники и зависимости
- Отдельные справочники объектов, зон, этажей, участков пока можно не выносить в MVP.
- На этапе 1 допустимы текстовые поля `zone` / `floor` / `section`.
- Единый внутренний справочник товаров должен быть основан на стандартной номенклатуре Odoo.
- Поставщики берутся из `product.supplierinfo`, но итоговый поставщик по строке выбирается вручную снабженцем.
- Опционально можно подставлять "последнего поставщика", но без автопринятия решения.

## 4. Статусы и жизненный цикл

### 4.1. Статусы документа
- `Черновик` (`draft`) - создание, импорт, первичная правка.
- `В работе` (`in_progress`) - сопоставление, разбиение на выдачу/закупку, резерв, частичные выдачи.
- `Закрыто` (`closed`) - все строки полностью обеспечены или обработаны вручную.
- `Отменено` (`cancelled`) - документ отменён.

### 4.2. Статусы строк
Пользовательские:
- `Частично выдано`
- `Полностью обеспечено`

Рекомендуемые технические признаки:
- `matching_required = true/false`
- `procurement_mode = issue/buy/mixed/manual`
- `qty_to_issue`, `qty_to_buy`, `qty_issued`

### 4.3. Переходы
- После создания и импорта документ остаётся в `Черновик`.
- После начала сопоставления или обработки строк переводится в `В работе`.
- После полного закрытия всех строк переводится в `Закрыто`.
- При отмене пользователем переводится в `Отменено`.

## 5. MVP vs Этап 2

### 5.1. MVP
- Создание документа по объекту.
- Импорт Excel фиксированного формата.
- Создание строк по зонам / этажам / участкам.
- Ручное сопоставление строк с внутренней номенклатурой.
- Пометка несопоставленных строк как "требует сопоставления".
- Заглушка экрана сопоставления.
- Выбор поставщика вручную снабженцем.
- Частичная выдача.
- Привязка документа к объекту.
- Печатная форма требования.
- Печатная форма выдачи / расходной накладной.

### 5.2. Этап 2
- Автоматический расчёт физического остатка.
- Автоматическое разбиение строки на `к выдаче` / `к закупке`.
- Резерв до фактической выдачи.
- Создание черновика RFQ с группировкой по поставщику.
- Обязательная ручная обработка строк без поставщика.
- Заглушка под согласование.
- Отчёты и аналитика.

### 5.3. Явная граница
- Цена в MVP не используется и не влияет на бизнес-логику.
- RFQ, наличие, согласование и отчёты не блокируют старт MVP.

## 8. Ключевые риски

- Отсутствуют готовые справочники объектов, зон, этажей и участков; возможна неоднородность данных уже на MVP.
- Формат Excel фиксирован, но реальные файлы могут содержать скрытые отклонения: объединённые ячейки, иные единицы измерения, пустые строки, дубли.
- Сопоставление по внутренней номенклатуре без нормализованного мастер-справочника может дать высокий процент ручной обработки.
- Частичная выдача и резерв в Odoo требуют аккуратной связи с `stock.picking`, иначе возможны расхождения между документом и складскими движениями.
- Если у товара несколько поставщиков и нет жёсткого правила выбора, строки закупки могут зависать в неопределённом состоянии.
- Статусы строк в требованиях описаны неполно; если не зафиксировать техсостояния, UI и отчёты будут спорными.

## 9. Open questions

- Что именно является "объектом": отдельная модель проекта, analytic account, складской объект или временный справочник модуля?
- Нужен ли отдельный справочник зон/этажей/участков уже в MVP или достаточно текстовых полей?
- Допустимо ли в MVP вручную переводить строку в `issue` / `buy` без расчёта остатка, если этап 2 заявлен как отдельный?
- Как трактовать строку без внутренней номенклатуры, но с выбранным поставщиком: разрешать закупку до сопоставления или запрещать?
- Должен ли кладовщик редактировать все поля строки или только подтверждать выдачу и корректировать фактическое количество?
- Что считается условием закрытия документа: все строки `Полностью обеспечено` или допускается ручное закрытие с остатком?
- Нужна ли мультикомпанейность и привязка к конкретному складу уже в первой версии?

## 10. Критерии готовности

### MVP ready
- Прораб может создать документ по объекту.
- Excel загружается без ручного редактирования исходного шаблона.
- Несопоставленные строки видны и доступны для ручного сопоставления.
- Можно частично выдать материал и напечатать документы.
- Документ и строки прозрачно связаны с объектом.

### Этап 2 ready
- Система сама считает физический остаток.
- Сама делит строку на выдачу и закупку.
- Формирует draft RFQ по поставщикам.
- Поддерживает workflow согласования и отчётность.
